## 内核崩溃栈（完整版，pstore dmesg-ramoops）

- 归档：`CPP12s-20260918-w1-panic.dmesg-ramoops-0.log`（Oops#1 Part1，完整 PC/寄存器/Call trace）、
  `.dmesg-ramoops-1.log`（Panic#2 Part1，SMP stop 流程）。
- 崩溃点：`rt_mutex_adjust_prio_chain+0x1b0/0x14c0`（静态 VA `_text+0x1777ab4`，`_text=0xffffffc008000000`），
  故障指令 `ldapr w8, [x27]`（静态镜像 `ldar w8, [x27]`，启动期 alternatives 替换）。
- Call trace：`rt_mutex_adjust_prio_chain` ← `rt_mutex_adjust_pi` ← `__sched_setscheduler`
  ← `__do_sys_sched_setattr` ← `__arm64_sys_sched_setattr`。
- 崩溃线程：`CPU: 1 PID: 22354 Comm: libghostlock.so`——**就是攻击进程**（native 经 PID namespace 看到的
  pid=14503，全局 PID=22354；`Comm` 明确）。**触发者是攻击自己的 `consumer_thread` 的 `sched_setattr`**，
  CPU1 即 consumer_cpu。前一版"崩溃线程非攻击进程"的推断作废。
- 触发链：`sched_setattr(tid=waiter 线程)` → `__sched_setscheduler` → `rt_mutex_adjust_pi(task)` 读
  `task->pi_blocked_on`（`x28=ffffffc03edbbb18`，waiter 线程内核栈上的 ghost waiter）→
  `next_lock = waiter->lock = 0`（`x25=0`）→ chain walk 内 `next_lock != waiter->lock`（0 == 0）
  一致性检查通过 → `lock = waiter->lock; raw_spin_trylock(&lock->wait_lock)`
  （[4]/[5] 无 NULL 检查）→ 读 `[NULL]`（fault VA 0，`WnR=0`）→ `panic_on_oops`。
- 关键寄存器：`x19=ffffff80458d0000`（waiter 线程 task_struct），`x21=task+0x10`（usage），
  `x24=task+0x884`（pi_lock），`x28=ffffffc03edbbb18`（栈 waiter），`x23(orig_waiter)=0`，
  `x1(chwalk)=0`（FULL_CHAINWALK），`x27/x25=0`。
- 决定性结论：**consumer 触发时 `waiter->lock` 就是 0**——stamp（setsockopt）本应把它写成 payload 的
  `fake_lock`（非 0）。即该运行时"stamp 未落地/已被覆盖"。
- 时间线自洽：native `boot_ms=341882`（BOOTTIME）+ T+6819ms ≈ 348.7s；ramoops 内核时间 302.484s，
  差 ≈ 46s 为该 boot 的 suspend 时间，确认本栈属于 CPP12s 运行。

## 机制分析（multicast 原语）

- one-shot 由 `waiter_thread` 执行：`FUTEX_WAIT_REQUEUE_PI` 超时返回后（`race_route_wait_ms=1000`），
  同线程 `setsockopt(MCAST_BLOCK_SOURCE)`；`ip_setsockopt()` 的 `group_source_req greqs`（264 字节）
  应覆盖同一内核栈上残留的 ghost `rt_mutex_waiter`（`stamp[0x60]` 与 waiter 起点对齐），
  写入 `task`/`lock`，随后 `consumer_thread` 的 `sched_setattr` 走 `rt_mutex_adjust_pi` 完成 PI 写。
- 本次 `lock` 仍为 0，候选原因：
  1. `setsockopt` 返回非 0（失败），而当前代码**无论返回值都设置 `consumer_go` 并执行 PI walk**；
     若失败发生在 `copy_from_sockptr` 前后未写入 greqs，waiter 保持 0 → 必然 panic。
  2. `setsockopt` 返回后到 `sched_setattr` 读取之间，ghost waiter 所在内核栈被中断/栈复用覆盖
     （waiter 与 consumer 同 pin 在 CPU1，存在调度/中断窗口）。
  3. stamp 布局未命中（本次未重现成功路径的重叠）——与 1/2 共享"同一二进制一次崩溃一次通过"特征。
- **安全缺口**：`do_kernel5_fake_lock_route` 与上游移植在 `setsockopt` 失败时仍触发 consumer；
  命中候选 1 时会把"stamp 未落地"直接暴露为内核 NULL deref。

## 处置

- 保留 `CPP12r` 的回退（2/2 先例）；分层/namespace 重试推迟。
- 已实施 hardening（`do_kernel5_fake_lock_route`，`src/core/routes/route_operations.cpp`）：
  `setsockopt` 失败时不触发 consumer，直接 `ROUTE_FALLBACK_SAFE` 返回，堵住候选 1 的确定性坏路径。
  构建：native `6713fba0f2643dbf52ac985de8101880f99e6d56c371c4828c8ad60360e7634d`、APK 285；
  形状对比：`do_kernel5_fake_lock_route` 155→162 指令（安全分支），其余 7 个攻击关键函数
  strict/形状一致（仅 `.text` 位移）；主机测试与 `lint-tidy` 通过。**待干净 boot 两次冷机门禁。**
  候选 2 的中断窗口属原语残余风险，另记诊断轨迹与缩短窗口方案。
- 先验证环境：设备静置/深冷启动后，回退版 `395c5faf…` 连续（至少一次）PASS 后再评估继续。
- 若环境持续 panic，暂停所有 Multicast 设备门禁，转向主机侧收尾（CPP14 文档/UML/函数表）。
