## 3 规格（未来形态；歧义处一律「选项 + 代价 + 建议」）

### 3.1 调用点编号与命名 `plugin_fork_<n>`
> **语义（2026-10-06 用户裁决）**：编号 = **执行时间轴上的位置（事件发生点）** ⇒ 语义是「**何时发生**」；**不是优先级** ✗、**不是择优/决胜/tie-break** ✗、**不是可让插件争抢的权重** ✗。
> **沿革（不删历史）**：用户最初的说法是「调用点数值也可以有**隐式的类似 priority 的含义**」⇒ **2026-10-06 用户更正为「事件轴 / 时间轴」**（先写「事件轴」，随即自我更正为「**时间轴**」）⇒ **以「时间轴（事件轴）」为准**。

- **形态**：**整数编号 + 统一前缀**（`plugin_fork_1`、`plugin_fork_2` …）；编号是**唯一标识**，名字是**展示**（`plugin_fork_<n>` 即规范拼写）；
- **上界（建议，待确认 P1）**：用户说「多达上百」⇒ **建议上界 256**（`u8` 可承载、留余量；若用 `u16` 则 1024，但会鼓励碎片化）⇒ 选项：固定 256（建议）/ 1024 / 不设上界（不建议：校验与 UI 无界）；
- **连续性**：**不要求连续**（backend 只声明自己用到的编号）；**但要求「保留段」明确**（见下）；
- **保留段（建议，待确认 P2）**：`1–49` = **普通调用点**（backend 自由使用）；`50` = **阶段转换点示例：root 权限可用**（用户原话的魔法点）；`51–255` = **保留给后续阶段转换点与 backend 专属点**；⇒ 具体切分**由用户裁决**；
- **与既有四点的映射（建议）**：**既有四点 = 具名别名，落到具体编号**——`PRE_SPAWN → plugin_fork_10`、`POST_SPAWN → plugin_fork_20`、`PRE_TERMINAL → plugin_fork_40`、`POST_TERMINAL → plugin_fork_60`（示意）；**避免两套词汇并存**（插件作者可能见过 `PRE_SPAWN`，必须能一一对应；映射表**一处定义**，禁止两处各写一份）；
- **与 `PRE_ROUTE` 的关系**：`PRE_ROUTE` **保持保留且必须拒绝**（`registry.hpp:45-46`）⇒ 在编号表里把它标为 **reserved/unused**（不分配编号或分配后标注「永不可用」）。

### 3.2 魔法值 = **时间轴上的里程碑事件**（阶段转换点）

> **语义（2026-10-06 用户裁决）**：所谓的「魔法值」= **时间轴上的里程碑事件**（milestone），例如「**waiter 关闭**」「**root 可用**」「**LKM 驻留窗口开始 / 结束**」⇒ 它们标记的是**时间轴上的位置**，**不是**配置层的优先级。

- **定义方式（选项 + 建议）**：① **编号即语义 + 具名符号表**（建议：编号是机制，具名符号是文档/诊断用；一处表定义）② 只有具名符号（不建议：用户明确要用编号表达「上百个点」）③ 只有编号（不建议：可读性差）；
- **最小集合（建议，待确认 P3）**：`root 权限可用`（= 用户示例的 `plugin_fork_50`）、`waiter 已关闭`、`LKM 驻留窗口内`（43284 的 `POST_TERMINAL`）、`LKM 卸载后`；四点各自**可判定**（见下）；
- **硬约束（R1，不可协商）**：**PI waiter 存活期不得 open 插件**（既有 R1）⇒ **任何阶段转换点都必须晚于 waiter 关闭**；`waiter 已关闭` 之前的点**只能**用于「不触碰插件运行时」的用途（例如日志/统计），**不得**触发 `.so` 映射；
- **可判定性（插件如何知道某魔法点已过）**：由**接口提供当前阶段**（见 §3.5）——插件在每次回调里读取「当前阶段编号」，**不需要自己推断**；⇒ 禁止「插件靠编号大小猜阶段」（编号与服务端阶段是两个维度，见 §3.4 的边界）。

### 3.3 backend 声明其支持的调用点

- **声明位置（选项 + 建议）**：① **编译期声明**（backend 属性：它**能**派发哪些编号）+ **用户可再收窄**（profile 里只选子集）**（建议）** ② 只放 profile（不建议：用户可写任意编号 ⇒ 与「代码是否接线」混淆）③ 只放编译期（不建议：无法按设备/路径收窄）；
- **与既有语义的关系（必须写清）**：`available`（profile）= **用户选择面**；native 的组合目录（`src/core/pipeline/orchestrator.hpp:41-52`、`component_catalog.hpp:29-69`）= **编译期接线事实**；⇒ **支持的调用点集合 = 编译期声明（能力）∩ profile 收窄（选择）**，**用户不得放宽**（只能变窄）；
- **数据形态（建议）**：每 backend 一段「支持的编号集合」（列表或位域文本），**与 `execution_paths`（§设计稿 §2.12）同族**——**一份数据一处真相**，供 UI 与校验消费；HOCON 片段示意：

```hocon
backend { cve_2026_43499 { plugin_forks = [ 5, 14, 25, 50, 51 ] } }   # 该 backend 能派发的编号
```

### 3.4 编号 = **时间轴位置**（**不是优先级**）；与 `available.priority` 的划界

- **建议语义（方向待确认 P4，不由本稿决定）**：编号表示**执行时间轴上的先后**——**越小越早** 或 **越大越早** 二者之一，**由用户裁决**；无论哪个方向，**顺序即发生先后**，**不是**「谁优先被选中」；
- **对照表（两轴不得互相解释）**：

| 维度 | `available.priority`（profile） | `plugin_fork_<n>`（插件调用点） |
|---|---|---|
| 所属轴 | **选择轴** | **时间轴（事件轴）** |
| 语义 | 多条路径中**谁被选中 / 谁默认**（决胜、tie-break） | backend 执行到**哪一个事件点**（何时发生） |
| 取值来源 | profile 的 `available` 条目 | backend 的调用点声明（§3.3） |
| 消费者 | UI 树排序、默认项选择（§设计稿 §2.1.1） | 插件派发时机、阶段判定（§3.2/§3.5） |
| 是否可以互相推断 | **否** ✗：不得因为编号小而认为该点在配置上「更优先」 | **否** ✗：不得用 `available.priority` 推断调用先后 |

- **禁止的用法（逐条）**：① 用编号决定「选哪条路径」；② 用 `available.priority` 决定「先派发哪个点」；③ 把编号当作可争抢的权重 / 插件可修改的排序键；
- **沿革（不删历史）**：曾以「**隐式的类似 priority 的含义**」描述编号（用户最初说法）⇒ **2026-10-06 用户更正为「事件轴 / 时间轴」** ⇒ 全部措辞按**时间轴位置 / 事件顺序**表述；
### 3.5 插件接口（必须提供「当前 backend + 其可用调用点」）

- **要求（用户明确）**：接口**同步提供**：**当前执行的 backend** + **该 backend 可用的调用点集合**；
- **形态建议（C ABI，尾部追加 + `size` 判定）**：在 `glk_contract_ops` 尾部追加（示意，**冻结期只设计不实现**）：

```c
/* 追加字段（示意）：size 判定以决定调用方/被调方是否看见这些字段 */
const char *backend_id;        /* 当前执行的 backend（例 "cve_2026_43499"） */
uint32_t    fork_id;           /* 当前调用点编号 */
uint32_t    stage_id;          /* 当前阶段（含魔法点语义，见 3.2） */
const uint32_t *forks;         /* 该 backend 可用调用点数组（升序） */
uint32_t    forks_len;         /* 数组长度 */
```

- **兼容策略**：结构体**尾部追加** + `size` 检查（旧插件看不到新字段；新插件需按 size 判定字段是否存在）——与既有 `size`/`abi_version` 设计一致；
- **禁止**：把**运行时密钥 / SPI / 端口**放进该接口（与既有「静态策略进文档、运行时密钥走会话帧」的隔离规则一致）；接口只提供**执行上下文标识**与**能力位/调用点**，不提供秘密。

### 3.6 执行模型

- **触发方式（选项 + 建议）**：① **backend 主动「打过某编号」⇒ 派发**（建议：与既有 `PluginStageSink` 派发模型一致，零内核插桩）② 内核插桩（不建议：攻击路径改动 + 真机门禁成本高）③ 轮询（不建议：时序不可控）；
- **fail-soft**：插件失败**不得**使攻击链失败（既有约定）；**无插件 ⇒ 零新增字节**（既有约定，必须保持）；
- **上百个点的性能/审计取舍**：编号只表示「可能被派发」，**实际开销 = 已注册插件 × 实际派发点**；⇒ 建议：**派发点内联判定「有插件才进入」**（零插件零开销），并对**每个点**记录「是否派发过」的有界诊断（与 `DiagLine` 同族，≤256 B/行）；
- **审计**：建议提供「本次执行实际经过的编号序列」日志（可关闭），用于排障与门禁核对。

### 3.7 与冻结状态的关系

### 3.8 **触发守卫：声明的编号必须真的会被触发**（Lead 建议，待用户确认 P9）

- **规定**：**backend 声明的每一个编号，都必须在执行中真的会被触发**——「声明了却永不触发」= **静默失效**，视为缺陷；
- **为何要立这条**：本会话已抓到**三个同族「静默失效」缺陷** ✗——① 导出 `.bin` **静默丢队列**（M5 前 `NativeProfileDocument.from()` 只读声明路径）；② **空段过滤器静默丢「唯一载荷是 queue」的段**；③ **kind 被默认偏好静默覆盖**。⇒「**声明了却永不触发**」正是同族**第 4 个**温床 ⇒ **必须用守卫堵住**；
- **可判定证伪（两层）**：
  - **静态层（必须）**：每个声明的编号**必须能在调用点表里找到对应项**（编译期或 host 测试断言「声明集合 ⊆ 调用点集合」）；
  - **运行时层（理想）**：跑一次覆盖样例（host 测试或真机门禁）⇒ 断言**实际触发过的编号集合 ⊇ 声明集合**（未触发即 FAIL，给出缺失编号清单）；
- **与 §4 的关系**：§4 第 1 条「未声明即不派发」是本条的**反向**守卫——两条合起来才闭合（**声明 ⇔ 触发**）。

### 3.9 **R1 禁止区间：由编号结构保证，而不是靠人记**（Lead 建议，待用户确认 P10）
### 3.10 **改进版建议：里程碑（语义标签）+ 每 backend 追加式槽位**（Lead 提案 / **待可行性审查**；不得写成已决定）

**它要解决的弱点（现方案 = 单个全局整数编号空间）**：
1. **全局整数是假抽象**：`43499` 的 `25` 与 `43284` 的 `25` **毫无关系**，却共用一个编号空间 ⇒ 读者会误以为可比；
2. **魔法值跨 backend 不可能都对**：「何时 root 可用」取决于**该 backend 自己的链**（43499 的 W1/W2/W3 与 43284 的 pagecache/ipsec 步骤不同）⇒ 一个全局编号无法同时对两个 backend 成立；
3. **编号无类型、无载荷契约**：编号只是数字，**不表达**「此刻允许读什么」；
4. **重编号即破坏**：在中间插入一个新点会让**其后所有编号漂移** ⇒ 已发布插件的订阅全碎。

**建议形态（两层）**：
- **里程碑（milestone）**：**具名**、**跨 backend 通用**、**由每个 backend 声明「会 / 不会到达」**——建议最小集合：`WAITER_CLOSED` / `ROOT_AVAILABLE` / `LKM_RESIDENT` / `SECCOMP_OFF`；语义 = **时间轴上的位置**（§3.2/§3.4）；
- **槽位（slot）**：**每 backend 私有**、**追加式整数**、**允许留空**、**永不重编号**——语义 = 该 backend **自己的**事件精度点（对应现方案的「上百个调用点」）；
- **插件订阅方式二选一（可混用）**：订**里程碑** ⇒ **可移植**（跨 backend 语义一致，但精度粗）；订**槽位** ⇒ **保精度**（backend 私有，换 backend 需改订阅）；

**配套规则（建议）**：
1. **只追加 / 永不重编号 / 可留空**（留空编号保留占位，不复用）；
2. **每点一个「载荷契约」**：声明该点**允许读取什么**（有界、版本化）；**运行时密钥 / SPI / 端口一律不进** ✗（与既有会话帧隔离规则一致）；
3. **接口补运行时状态**（在 §3.5 的「当前 backend + 可用调用点」之外）：**已通过的里程碑** + **时间轴游标位置（已到哪个槽位）** + **即将到达的下一里程碑**；
4. **与 §3.8 触发守卫联动**：backend 声明「会到达里程碑 M」⇒ M **必须真的到达**（未到达即 FAIL）；声明「不会到达」⇒ 到达即 FAIL；
5. **与 §3.9 R1 禁区联动**：禁区以**里程碑**表达（`WAITER_CLOSED` 之前 = 禁区），**与编号大小解耦** ⇒ 即使槽位编号方向/取值变化，禁区仍然成立。

**一句话对比表（原方案 vs 改进版）**：

| 维度 | 原方案（单个全局整数编号） | 改进版（里程碑 + 每 backend 追加槽位） |
|---|---|---|
| 顺序语义 | 全局编号即顺序（跨 backend 混读） | **里程碑 = 跨 backend 语义**；槽位 = **backend 内**顺序 |
| 顺序变了会不会碎 | **会**（中间插入 ⇒ 其后全漂移） | **不会**（只追加、永不重编号；里程碑具名） |
| 插件可移植性 | 差（编号含义随 backend 变） | 好（订里程碑即可移植；订槽位则自愿放弃可移植性） |
| 声明失效风险 | 高（声明了但语义对不上也看不出来） | 低（**会/不会到达**是**可判定声明** + §3.8 守卫） |

> **状态**：以上为 **Lead 提案，待可行性 / 可维护性审查** —— **不得据此实现**（插件工程仍冻结）；审查通过前**不写入契约**。

- **既有硬约束（R1）**：**PI waiter 存活期不得 open 插件**（见 `docs/plan/branch-plan.md` 的冻结/恢复清单与契约 §3.14.7）；
- **编码进编号空间**：把「**waiter 关闭**」定义为**时间轴上的里程碑**（§3.2）⇒ **该里程碑之前的编号段 = 禁区**：插件**不得**在这些编号处被打开（派发同样禁止，因为打开是派发的前提）；
- **理由（本会话教训）**：**靠人记的约束一定会破** ✗ ⇒ 让约束**由编号结构保证**：禁区是**编号段的属性**，任何 backend 声明落在禁区 ⇒ **静态检查即拒绝**（不依赖运行时自觉）；
- **可判定证伪**：① backend 声明一个**落在禁区内的编号** ⇒ **必须 FAIL**（配置/编译期检查拒绝）；② 在禁区编号处尝试 open ⇒ **必须拒绝**并给具名诊断（沿用既有 R1 的 fail-closed 语义）；③ 把「waiter 关闭」里程碑**人为后移**（若将来变动）⇒ 禁区随之扩大，**原先合法的声明必须变成 FAIL**（证明约束确实由结构驱动）。

- **本文档不触发解冻** ✓；恢复仍以 `branch-plan.md` 冻结清单（逐条 file:line）为准：**撤销注释 + 跑门禁**；
- **解冻后的建议顺序（每步独立门禁）**：① **接口字段**（ABI 尾部追加 + size 判定 + 单测）→ ② **backend 声明**（编译期支持集合 + profile 收窄校验）→ ③ **派发**（按编号派发 + fail-soft + 零插件零字节回归）→ ④ **阶段转换点语义**（R1 约束下的点集合）→ ⑤ UI/文档（树与本地化，若需要）；
- 每一步的门槛沿用既有纪律：host/lint/NDK + **真机门禁**（触及攻击路径时）+ 负例/证伪。

## 4 验收 / 证伪（未来执行时用）

1. **未声明即不派发**：backend **未声明**编号 N ⇒ 在 N 处**不得派发**（可断言：注册了插件的 N 不产生调用）；
2. **魔法点之前的能力请求必须失败**：在「root 可用」之前请求 root 能力（或请求后续阶段才有的动作）⇒ **必须拒绝**（fail-closed），并给出具名诊断；
3. **接口 backend 必须与实际一致**：接口里提供的 `backend_id` 与本次实际执行的 backend **不一致 ⇒ 必须失败**（不可静默）；
4. **R1 守卫**：在 waiter 存活期请求 open 插件 ⇒ **必须拒绝**（沿用既有 R1）；
5. **零插件零新增字节**：未注册任何插件时，全链路**逐字节不变**（与既有回归同规）。
6. **触发守卫（§3.8）**：backend 声明了编号 N ⇒ **N 必须在覆盖样例里真的被触发**（未触发 ⇒ FAIL 并列出缺失编号）；反向：未声明编号被触发 ⇒ FAIL；
7. **R1 禁止区间（§3.9）**：backend 声明落在「waiter 关闭」之前的编号 ⇒ **必须 FAIL**（静态拒绝）；在该段尝试 open ⇒ **必须拒绝**（fail-closed 具名诊断）；
