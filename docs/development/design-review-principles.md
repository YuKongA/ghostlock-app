## 0. 第一审查门：在保留批准职责的前提下简化（v0.5）

本节是 §3 的判断依据，不是额外审核轮次。`design-critic` 先核对已批准目标、职责和本批缺口，再比较保持同一合同的直接方案，最后审机制自洽。没有用户价值不值得做；机制少也不自动正确。只有保持相同批准行为、成功含义、失败/资源终态与依赖边界的方案，才参与复杂度比较。

<a id="review-design-choice"></a>

### 0.1 默认选择

- **先看调用者怎样使用，再定接口与机制**：从已批准职责和本批承诺出发，在原设计处引用受影响的真实调用者，说明它的入口、输入、返回/副作用，以及失败、取消后的资源归属与终态；再推导必要类型、接口和组件。新功能可用本批拟议或已批准的具体使用场景与简短调用草图，保留原批准状态，不要求先实现 caller 或另交模板。caller 是实现证据，不是需求来源；缺少现有 caller 不取消已批准但未接通的职责。
- 先说明满足上述用法的直接方案；更复杂方案才按 [§2](#review-cbn) 说明它为何不能满足当前合同。“以后可能需要”“更通用/更安全”或方案已写完，都不单独证明新增机制必要。
- 先确定职责与 owner，再在保持它们的可行方案中优先具体类型和直接调用。单 caller、单方法只提示检查转发成本，不证明职责可删。新增接口/中间层须对应真实平台或所有权边界、当前复用，或已批准且本批需要的变化轴；保留已批准职责不等于提前实现全部未来能力。
- **扩展点（C2）**：只有当前已有两个实现/consumer，或用户已批准且同批交付的第二变化轴，才要求写扩展点；不为假想 op/backend/route/landing/执行器/脚本类型预建结构。未来需求到来再按证据重构，不恢复旧“每个新结构必须预留扩展点”。
- 测试便利性不能单独证明生产抽象有必要；优先在已有平台/副作用边界放置 test seam。
- 提议删除/绕开组件时，区分“能力已取消”“能力未实现/未接线”“实现重复”。删除能力需取消依据；删除实现需具名新 owner 承接行为与失败合同，批准职责不得悬空或出现双 owner；转移须有依据。源码不可达、类数减少或测试删完均不单独关闭产品项。纠正及临时指令的执行细则只引用 [工程规范 §1.1](engineering-standards.md#engineering-execution)。

### 0.2 阻断形态

下列形态触发必要性核查，不自动证明可以删除。审查者先定位受影响职责及本批后果，再提出保持同一合同的删除/合并候选；简化若转移已裁定 owner 或改变成功含义，应按变更提案处理，不能当成必须执行的“修法”。满足 §3.1 的阻断条件后才阻断：

1. 同一有序数据流存在两层及以上queue、sequence或drainer，但各层没有不同的owner、背压合同与独立终结点。
2. 上层与下层各维护一份表达同一生命周期的状态机，或用claim/abandon/timeout补偿本可由单一owner直接管理的资源。
3. interface/adapter/executor/registry/converter只转发一次调用，既不隔离真实边界，也不消除caller分支或重复实现。
4. 为尚不存在的backend、CLI、平台、provider或第三个实现预建公共合同、配置项、兼容层或动态发现机制。
5. 用timeout、重试、后台monitor或额外worker修补所有权不清；能先明确owner与终结顺序时，必须先简化所有权。
6. 新机制带来的类型、状态、并发边、测试矩阵与文档责任多于它删除的重复/分支，却没有有依据的当前收益或风险降低说明。

### 0.3 按需说明，不固定填表

已有目标、职责、缺口与选型理由直接引用；只追问影响本批判断的缺口。真实复杂取舍按 [§2](#review-cbn) 写在原设计处，不填首轮五项表、机制计数或重复前言。简化仍须满足 §0.1 的合同等价条件，不以删职责代替降复杂度。

<a id="review-scope"></a>

### 0.4 滚动细化：需求记录不等于本批承诺

改或建计划前，从Beads当前任务的spec_id、OpenSpec设计及[语义代号入口](documentation-standards.md#work-identifiers) 定位相关在办计划，判定无冲突／重复／被推翻；重复则并入，被推翻则标注取代关系，不允许两份权威并存（2026-10-10 用户裁定）。

在**所属OpenSpec的目标/设计与Beads的原生任务状态**内区分以下三种范围；不新建 backlog 系统、审批角色或逐需求附件。开发者明确需求保留原文、来源及后继裁定，旧清单归档后只作历史，不恢复第二个当前入口。

| 范围 | 记录到什么程度 | 何时进入当前批次 |
|---|---|---|
| 本批承诺 | 已批准目标、必要依赖、改动范围、验收条件 | 沿用现有 S/M/L 批准权限；实现前足够明确 |
| 后续需求 | 用户目标/来源、已知约束、待分析问题、owner 与重访触发 | 相关性/依赖分析、验收可说明且获原权限批准后纳入 |
| 待裁定 | 影响当前承诺的歧义或取舍及最小问题 | 只暂停受影响决策；不将未知自动当作本批实现任务 |

- **近细远粗**：前期侦查、需求被认可、写在同一计划，均不自动授权本批实现。后续需求不预写逐符号 TSV、不冻结完整状态机、不为假想接口建立抽象；不是遗忘、取消或完成。
- **纳入前只问实际依赖**：当前目标不实现它是否仍能独立验收？若能，留在后续；若不能，指出数据/合同/资源/安全依赖并把最小必要部分纳入，范围扩大仍需原权限批准。用户明确要求同批时不能自行延期，遇到不可行冲突一次说明并请求裁定。
- **已知未来约束现在评估**：后续已批准目标若影响当前难以逆转的接口、安全或容量选择，先做必要影响分析或最小可行性调查；不因此提前实现整个后续需求。未知但关键的依赖按 §3.1 处理。
- **承诺变更受控**：既有本批承诺不得悄悄重标为后续以躲过 gate；移出须记录批准、影响和重访触发。规范更新本身不改现有产品进度、既有承诺或真机欠账；旧计划仅在下一次实际触及时分类，不发动全库重写。
- **只细化即将实施的批次**：前批验收后，依据新证据细化下一批；同一批只解决一类目标及必要闭包。后续条目只作需求记录，不算本批未完成交付项。若当前 gate 无法判定而尚未实现，修正边界/补足设计，不先写未分析充分的生产代码来换取审核通过。

依据：教材 §4.2 需求基线与变更、§5.2 策划逐步细化、§7.1 设计贯穿开发；这是原 Explore→Design→Implement→Verify 内的范围规则，不是新增生命周期。

<a id="review-feedback-control"></a>

### 0.5 纠偏如何改变下一动作（复用原目标、进度与验证矩阵）

只核对纠正是否改变下一动作，不另做复盘报告。下表定位唯一执行条款；相关事实写回原目标、进度或验证矩阵，不复制第二份流程。

| 遇到的问题 | 本次要核对什么 / 直达规则 |
|---|---|
| 重划 owner、删除或合并机制 | [§0.1](#review-design-choice)：从用户结果反推执行链，区分保留/转移/取消，核对职责承接，不把缺接线当能力取消 |
| 同批混入弱依赖需求、为不可用旧连接预建兼容 | [§0.4](#review-scope)：是否为当前验收必要依赖。兼容仅服务须支持的实际调用者/数据或明确合同；技术选择先用具名纵向使用者验证，不迁移未批准的所有 backend |
| 用户纠正、停止、暂缓验证未进入下一动作 | 执行者按 [工程规范：指令执行](engineering-standards.md#engineering-execution) 更新直接消费入口；审查只核新裁定生效、原欠账与恢复触发未丢失 |
| 反复扫描、SHA、换环境或评审 | 调查按 [取证与停止](engineering-standards.md#engineering-investigation)，复审按 [§3.2](#review-incremental)；核对本次新增证据是否会改变决定，不重做上述步骤 |
| UI 反馈反复出现、局部 PASS 被当最终完成 | 按 [证据与可观察关闭条件](#review-evidence-closure) 核对指定场景及对应运行结果，而非源码已改或编译已过 |

上述表是对本项目反思的裁剪：参考 [Google SRE 复盘](https://sre.google/sre-book/postmortem-culture/)把注意力放在促成错误的条件与预防动作，而非责备个人；参考 [NASA 需求检查](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)的目标追溯、适当层级与可验证性；参考 [Google 审核内容](https://google.github.io/eng-practices/review/reviewer/looking-for.html)对设计、用户行为和过度设计的区分。不导入独立复盘系统、会议、量化打分或新的批准门。

## 1. 原则清单（按疑点查阅）

A–G 保留原身份与锚点；已有权威条款的项仅作直达索引。只有涉及该性质时才读目标条款，不沿每个链接递归通读。

### A. 简并与去冗

<a id="review-a1"></a>

- **A1 同一事实只写一处**：按 [R1：单一权威](engineering-rules.md#r1) 检查重复表述；本文是审查入口，不另定一套权威规则。
- **A2 取代而非叠加**：按 [R27 取代制](engineering-rules.md#r27) 与 [文档归档](documentation-standards.md#documentation-process) 核对唯一现行版本；旧 requirements/Q10 仅作沿革。
- **A3 完整与内聚**：按 [R30](engineering-rules.md#r30) 直达 [文档规范：篇幅与拆分](documentation-standards.md#documentation-length)，不另设配额。
- **A4 一个概念一个名字**：同一结构出现两个名字即视同缺陷，必须合并或明示同源（`= 原名` + `static_assert`）。

### B. 单一权威与一处读取

<a id="review-b1"></a>

- **B1 每事实一处权威**：旧号保留为 [A1：单一权威检查](#review-a1) 的入口；生成/对拍要求仍由 [R1](engineering-rules.md#r1) 定义，理论说明见 [E-REVIEW-RULE-003/§3](design-philosophy.md#philosophy-authority)。

<a id="review-b2"></a>

- **B2 一处读取**：读取路径、并存时的逐值等价对拍与回退声明按 [R2](engineering-rules.md#r2)。沿革：载体/声明双读取曾使导出 `.bin` 静默丢队列。
- **B3 一处权威图**：执行 [文档规范：画图](documentation-standards.md#documentation-diagrams)，不另复制结构图或维护规则。

### C. 最小化与必要性

- **C1 最小改动**：授权文件范围与冻结项直接按 [工程规范：批次/保留项](engineering-standards.md#engineering-batches) / [冻结组件](engineering-standards.md#engineering-preserved)。

<a id="review-c2"></a>

- **C2 当前变化轴优先**：扩展点判据只在 [§0.1](#review-design-choice) 维护；v0.3 已取代旧“每个新结构必须预留扩展点”。
- **C3 成本权衡（2026-10-07 用户口径）**：编译期收益与工程成本的取舍按 [§2](#review-cbn)，不另填 CBN 表。
- **C4 不做无收益抽象**：必要性按 [§0.1](#review-design-choice)，远期需求按 [§0.4](#review-scope)，不重复定义扩展条件。
- **C5 临时物零容忍**：实验入口与实际临时物的清理按 [工程规范：实验](engineering-standards.md#engineering-experiments) / [代码修改](engineering-standards.md#engineering-code-editing)；一般规则为 [R23](engineering-rules.md#r23)。这是项目裁定，不是讲抽象与模块化的教材 §6.2。

### D. 可验证性（**D1 为准**）

<a id="review-rule-d1"></a>

- **D1 判据形式 = 需求场景 + 等价类/边界 + 按风险选择白盒覆盖**（**取代** AGENTS「守卫/断言必须证明能失败」与 `engineering-rules.md` **[R10](engineering-rules.md#r10)**）：
  - **按合同设计断言**：合同来源及结构约束的例外按 [§3.1](#review-contract-boundary)。黑盒从需求和调用者接口设计用例，断言返回、错误、状态与副作用；白盒按内部结构选择分支、条件或路径覆盖。单元测试不自动等于白盒，必要的结构/编译期不变量仍可用 `static_assert`、表一致性等检查；
  - 审视用例的两类变化：合同行为出错时断言应识别；保持全部适用合同、只替换实现时不应无故失败。预期值来自需求，不由被测实现重算来证明自己；这是用例设计判断，不强制实际变异或故障注入；
  - 覆盖当前需求的正常/异常场景、有效/无效等价类及相关边界（0/1/MAX、空、超限、非法组合等）；边界不排除普通合法输入，操作和观察按 [工程规范 §8.0](engineering-standards.md#engineering-evidence)；
  - 复用已有有效用例，一例可覆盖多项需求；不可达用例可排除，但须有前提/不变量依据，不以主观“不可能”跳过真实失败模式；
  - **不再要求**为守卫/断言做**造错（证伪）实验**——该要求自 v0.2 起为**可选手段**而非门槛。
- **D2 判据分层**：入口与记录按 [工程规范：证据](engineering-standards.md#engineering-evidence)，命令直达 [§8.1](engineering-standards.md#engineering-gate-commands)，不在本文复制。

<a id="review-d3"></a>

- **D3 分层证据不越界**：必须满足 [工程规范：证据边界](engineering-standards.md#engineering-evidence) 与 [真机条件/归档/supported 判定](engineering-standards.md#engineering-device-gate)；AVD/host/静态检查不替代目标真机。设计批准不代表实现或设备 PASS；逐项关闭按 [§3.1](#review-evidence-closure)。（教材 §8.14–8.17）
- **D4 产物身份 + 新鲜度**：观测与代码矛盾时按 [R16](engineering-rules.md#r16) 核新鲜度及路径/字节/mtime/sha；SHA 范围直达 [身份核验](engineering-standards.md#engineering-identity)，普通审查输入只按 [G4](#review-g4)。
- **D5 实际结果全量计数**：执行 [工程规范：证据与三桶计数](engineering-standards.md#engineering-evidence)，不将交换格式或控制台尾部当作判据。
- **D6 具名诊断是契约**：阶段/原因标识的稳定性按 [R11](engineering-rules.md#r11)。
- **D7 fail-closed**：按 [R12](engineering-rules.md#r12) 检查失败是否被降级继续，不另定回退/重试例外。

### E. 结构约束与安全

<a id="review-e1"></a>

- **E1 边界与耦合**：层间优先显式数据合同；禁止窥探内部结构、以共享可变全局或下层读取上层内部标志驱动行为。显式协议命令、调度和回调不因含控制信息自动违规，须审合同与依赖方向；项目更严限制应指明适用边界和理由，不冒称教材全面禁止。（[R3](engineering-rules.md#r3)；教材 §6.3）

<a id="review-e2"></a>

- **E2 功能内聚**：一个可说明的职责，不等于函数/类物理不可再拆。拆分须同时评价接口、耦合与集成成本；不以模块数量或一句话长度判通过。（[R4](engineering-rules.md#r4)；教材 §6.2–6.3）
- **E3 编译期锁定**：组合/步骤集/终端的绑定与运行期检查按 [R6](engineering-rules.md#r6)。
- **E4 PI 窗口约束（实证版）**：**白名单/禁项以 [pi-window-constraints](../analysis/pi-window-constraints.md) 为准（口径 = `inside PI`：约束只覆盖 PI 内那几段，PI 之后可打印）** —— 实测死因 = 窗口内 `sched_setattr`（改 nice / SCHED_BATCH）进入内核 PI 链（`__do_sys_sched_setattr` → `__sched_scheduler` → `rt_mutex_adjust_pi`，见 device-gate `20260922-2231-CPP12x/CPP12s-*-panic`）。因此：**禁 `sched_setattr` / `setpriority` / `nice` 及任何会进入 `rt_mutex_adjust_pi` 的调用**；并保留**禁堆分配 / 禁间接分派 / 禁首次触页**（防御性条款）。窗口外允许虚接口（gate/计划/配置构造/终端交接）。

> **沿革**：原 E4 表述为「PI 窗口内禁间接分派/分配/首次触碰新页」（由 ADR-0001:183、ADR-0004:188-189、`route_lifecycle.hpp:9-11` 推下）—— 该理论条款**覆盖不到实测死因**；2026-10-08 按 device-gate 记录改写为「白名单 + 禁项」，原文保留于本行。

<a id="review-e5"></a>

- **E5 双读取路径 = 高危形态**：本仓 M5 事故的检查入口；判据统一引用 [B2：一处读取](#review-b2)，不重复定义。
- **E7 共享工作树保护**：Git 修改与等效写回禁令、只读比较方式直接按 [工程规范：文件操作](engineering-standards.md#engineering-file-operations)；保留 2026-10-07 事故后的硬规则身份。
- **E8 写回完整性（硬规则，同源）**：执行 [工程规范 §6.6：写回完整性](engineering-standards.md#engineering-file-operations)，不另定一套读写/备份步骤。

<a id="review-e6"></a>

- **E6 守卫可失败**：旧号保留为 [D1：验证覆盖](#review-rule-d1) 的取代指针；造错仍为可选加强手段（尤其是 vacuous 断言风险场景）。

### F. 记录与沿革

- **F1 不删历史**：被推翻提法保留沿革与理由、用户裁决留记录；具体归档按 [文档规范](documentation-standards.md#documentation-process)，纠正落点按 [工程规范：指令执行](engineering-standards.md#engineering-execution)。
- **F2 技术债预判（v0.3 收窄）**：只记录当前方案已经明确产生的债、owner与偿还触发；未来可能新增的功能只作为触发条件，不授权今天预建扩展机制。登记到现有 decisions 或技术债位置，不因审核另建台账。
- **F3 强制确认须核沿革与技术债**：按 [AGENTS §1](../../AGENTS.md#e-review-rule-004) 核对两项记录；缺一仍视为未完成。
- **F4 决策可检索**：记录字段与存放位置只按 [§3.3](#review-output)，不再追加一份记录表。

### G. 事实与证据

- **G1 每条结论带依据**：引用 `file:line` 或具名规则，区分教材、项目裁定与个人建议；阻断举证统一按 [§3.1](#review-stage-blockers)，规则编号不能代替因果说明。
- **G2 禁止外部计划引用与未定义标签**：标签必须能在本族文档中找到定义（否则先补「标签 → 来源」表）。
- **G3 未核实项显式标注**：未知事实及最小核实路径按 [§3.1](#review-stage-blockers) 表述，不当作已证实缺陷。

<a id="review-g4"></a>

- **G4 审查前提 = 可识别输入**：记录 HEAD、时间、目标文件和本轮工作树 diff；HEAD 不代表未提交修改。hash 范围按 [身份核验](engineering-standards.md#engineering-identity)。相关 writer 停手后评审；审中输入改变仅使受影响结论失效，按 [§3.2](#review-incremental) 复核，不因无关写入全量重跑。

<a id="review-cbn"></a>

## 2. CBN：仅解释真实取舍，不设独立表

**C3 成本原则**：编译期收益必须与工程成本权衡；编译期/静态方案成本超过更灵活方案时，必须让路（2026-10-07 用户口径）。

只有保留/新增复杂机制、直接方案不能满足当前要求，或收益/风险存在实质争议时，才在原设计处说明：**为什么需要、直接方案为何不足、主要代价与风险**。已有论证直接引用；未解决的具体取舍才补充。

取消固定六字段、备选数量、数字收益、机制计数和翻转条件的填表要求。可测量的事实仍如实引用；不虚构数字，也不接受仅写“更安全/更通用”来替代必要性依据。合同、资源与真机判据不因此放宽。

<a id="review-execution"></a>

## 3. 审查执行与产出（沿用原岗位，不增加审批层）

<a id="review-task-boundaries"></a>

**独立设计审查由非作者、只读 critic 执行**；触发条件只按 [AGENTS §7](../../AGENTS.md#agents-review)。Lead 在原委派中区分以下任务，不把 design-critic 当作所有质量工作的总入口；未触发则继续原开发/测试流程，不另起 critic 证明“无需审核”。

| 任务 | 原职责与判断范围 | 不自动转成什么 |
|---|---|---|
| 设计判断 | 既有 design-critic 独立核本批目标、真实调用者、合同/owner/生命周期、失败语义、关键可行性及验收设计能否证明目标 | 不逐项代做普通代码审查、测试执行或台账维护；验收设计仍属设计判断，不因涉及测试而剥离 |
| 普通代码/测试审查 | 既有非作者评审核实现是否符合批准设计、测试断言是否有效、资源隔离/清理及覆盖是否充分 | 发现实现缺陷不自动重开设计；涉及实质设计修订、关闭条件改变或证据解释争议时，才按 §3.2 将该差异交原 critic |
| 机械核对 | 原执行者/Lead 复用已有工具与证据，核路径/格式/计数、台账状态同步和原条件的满足情况 | 不另设 TSV 审查岗或必经 PASS；原 finding 的关闭权限仍只按 §3.3，核对者不得自行改条件 |

三类是任务分工，不是串行阶段。按当前需要委派，复用原记录；已有有效检查和适用门禁照常执行。

<a id="review-author-self-check"></a>

### 3.0 作者自检（交付责任，不增设预审）

设计/代码作者（Lead 或子智能体）正式送审前必须检查并修正原交付，不把已有资料足以确认的基础问题交给 critic 补完。

- **设计自检**：按 [§0.1 的真实调用者用法](#review-design-choice) 沿受影响链路核对当前接口、owner 和失败/终结语义，再检查拟议方案；不得只复述类图或机制。范围只按 [§0.4](#review-scope)，不因自检扩大本批承诺。
- **合同与测试自检**：按 [§3.1](#review-contract-boundary) 识别必须保持的性质及消费者；涉及用例时按 [D1](#review-rule-d1) 区分行为断言与实现绑定，不把旧代码、fixture 或工具偏好反推成需求。
- **按阶段交证据**：设计阶段说明可行性、验证方法与预期结果；实现阶段核对最终 diff 和适用且获准的实际观察，按 [工程规范 §8.0](engineering-standards.md#engineering-evidence) 留可重放条件。未运行项如实保留，不提前索取尚未实现的 PASS；证据范围按 [§3.1](#review-stage-blockers)。
- **增量交付**：修订只自检差异及受影响合同；具名说明仍需判断的问题，不宣称风险已清零。复用证据、直接修原交付，不增加自检报告、状态、审批、岗位或前置 critic，不扫全库/全套规则。关键未知可定向咨询，不变成常规预审；自检不替代独立审查、用户批准和原门禁。

<a id="review-stage-blockers"></a>

### 3.1 先判阶段与影响，再判阻断

critic 先独立核对方案是否服务本批需求、职责和最新裁定，再查技术自洽；作者自检不免除独立判断，“阻断 0”不等于产品成功。每轮先确定“本批承诺、当前阶段、要过哪个 gate”。阻断须同时给出：**适用要求 + 当前阶段 + 证据位置 + 对本批验收/安全/关键可行性的具体后果或依赖链 + 关闭条件**。规则编号、模板缺项、工具报红或“尚未实现”本身不足以证明阻断；信息缺失写明待确认事实与核实路径，不当作已证实缺陷。关键缺证确实使当前决策无法成立时，可阻断该决策并指明最小补证。

**下表只说明已触发审查或原 finding 复核时应看哪些证据，不新增触发条件；“实现交付/验证”不表示每次交付都要再经 design-critic。**

| 当前阶段 | 应审证据 | 不提前索取 |
|---|---|---|
| 需求收集/前期侦查 | 用户目标、已知约束、未知问题、与当前批次的依赖 | 完整设计、逐符号 TSV、成套测试及生产实现 |
| 设计批准 | 当前需求→设计→验收映射、关键合同/owner、可行性、验证方法和预期结果 | 尚未进入实现阶段的完整 test source、生成结果或运行 PASS |
| 实现交付/验证 | 当前约定的实现、测试、必要工具/manifest、执行结果及身份 | 弱相关后续需求的实现；与当前变更无关的历史工具债 |

- **关键可行性不能后移**：若当前设计依赖未经证实的平台能力、接口或资源条件，先以必要来源证据或最小实验回答该问题；实验不授权提前实现后续完整需求，仍遵守原有实验入口与变更纪律。

<a id="review-contract-boundary"></a>

- **合同由要求与消费者确定，不由现有实现反推**：先指出本批必须保持的行为/性质、依据与实际消费者。返回、错误、可观察状态和副作用属于合同；已批准的 owner/生命周期、资源终结顺序、依赖边界、wire/ABI、身份与验收范围也可能是真合同，不因“用户看不到”而删除。私有 helper、类名、旧统计数字或输出措辞只有在明确合同或经确认需保留的消费者依赖下才锁定，存在于代码、测试断言或模板中本身不足为据。
- **test/TSV/工具问题按用途归因**：先说明“哪项合同→谁消费→怎样影响本批”。实际生成、构建、注册输入，以及已批准改动范围、删除边界或合同验证，仍按真实消费者和适用 gate 核验；缺陷可阻断对应 gate。仅审计展示、旧断言或远期清单不自动阻断业务设计。critic 默认不逐格审核全量 TSV/ledger，不把逐符号填满或表间字面一致当作设计成立的通用前提；只在具体范围、依赖或合同疑点涉及台账时查相关行，机械一致性按 [职责边界](#review-task-boundaries) 处理。finding 应指出范围越界、合同缺失或行为覆盖不足等实质问题，而非仅报“TSV 不完整”。误报按原权限修工具/fixture 的最小闭包，不为迁就旧实现扩建系统、改变产品行为、删除有效覆盖或伪造 PASS；真实规范冲突按 [AGENTS §1](../../AGENTS.md#e-review-rule-004)，变更已批准的工具合同仍须原权限批准。
- **设计者负责方案，critic 负责缺陷**：关闭条件写必须成立的性质，修法只作可选建议。多个方案满足适用硬合同且代价有依据时，尊重作者/用户选择，不遗漏用户已允许的可行选项，不仅因偏离 critic 优选就要求强制越权或登记技术债。critic 建议增加 owner/queue/state/worker 时，也须重新证明必要性，不强制唯一实现。

<a id="review-evidence-closure"></a>

- **按原条件、按证据所在层关闭**：操作、观察与重放口径只按 [工程规范 §8.0](engineering-standards.md#engineering-evidence)，在原 finding/验证矩阵关联具名用例或运行证据，不另建验收报告。raw uid 0、诊断、脚本 dispatch、Payload/Finish 与产品成功仍按各自批准合同判断；只核本批改动链段及必要集成，不每轮重跑整条产品链。用户反馈须对应其指定场景和可观察结果；新要求改变原合同的，先按范围变更处理。

<a id="review-incremental"></a>

### 3.2 输入、读取和复审

1. **输入直接引用**：提供原目标/判据、批准范围位置、本次 diff及仍需设计判断的未关闭项；裁定与欠账按需链接。台账查阅按 [合同与消费者](#review-contract-boundary)，不默认提交全量 TSV 逐格审查。作者自检按 §3.0，输入身份/停写/变更失效按 [G4](#review-g4)；不制作输入包或复制整份计划/聊天史。
2. **按影响读取**：首轮覆盖本次需求/职责、可行性、必要机制、接口/资源/失败及验证策略的适用风险；仅发现具体依赖或矛盾才扩读。不逐条输出“已检查/不适用”，不重审已裁定偏好；输入未变的结论复用。
3. **一次集中给结论**：返回当前已发现的问题，不故意分轮挤出；真实阻断先给可行动结论，关键缺证只索取最小证据并说明影响边界，不无限侦查。新事实揭示的风险仍须报告，不为减少轮数隐瞒。
4. **只复审需判断的差异**：实质设计修订、关闭条件改变或证据解释争议交 critic 定点复核；其余修复按 [§3.3](#review-output) 的原权限关闭，不再要求整轮最终审核。不按固定分钟自动批准，不因取消表格略过真实风险。

<a id="review-output"></a>

### 3.3 输出与关闭

**输出结论，不填写完整报告模板。**

- **无阻断**：一句“可进入对应批准 gate；阻断 0”，附覆盖边界；不宣称实现/真机通过，不输出空问题表或全量规则复述。没有未关闭阻断或新增实质问题、只剩台账/状态机械同步时，列明待同步事项，不因此将设计结论改为 `CHANGES_REQUIRED`；记录仍须如实完成。
- **有问题**：只列 `问题 ID｜级别｜位置/证据｜本批后果｜关闭条件`；复杂判断才展开，依据附对应项，不复制规范。问题 ID 按 [对象语义根](documentation-standards.md#engineering-identifiers) 分配。
- **关闭权限只在此定义**：每项明确“修复后需 critic 判断”或“按所列条件由 Lead 核对”。critic 明确指定可机械核对且原条件明确的修复，由 Lead 按原指定证据核对后记 finding ID＋证据指针关闭，即完成该项关闭，不再向 critic 索取重复 PASS 或全批最终确认；未形成设计 finding 的纯机械维护沿原职责完成，不为收尾新建 finding。这不是提前批准；修法简单不等于缺陷不阻断，真实阻断在满足原条件前仍有效。Lead 不得改条件或用编译通过替代指定运行证据；仍需判断的差异按 §3.2 回 critic。
- **阻断与建议分开**：阻断须满足 §3.1，未按原条件关闭不得过对应 gate。重要/建议不影响本批准出时不阻塞，也不为其另开复审；接受/反驳/延期保留实质理由，重复意见合并回应。
- **记录复用原位置**：保留时间、输入/版本、结论、阻断数及必要证据，不另建台账；副本/脚本/包装禁令按 [工程规范：文件操作](engineering-standards.md#engineering-file-operations)，强制越权核 [F3 所引裁定](../../AGENTS.md#e-review-rule-004)。设计、实现、运行、真机结论继续分开。

本次裁剪参考 [Google 审核速度指导](https://google.github.io/eng-practices/review/reviewer/speed.html)中减少等待与无谓再次批准的做法；机械关闭不豁免本项目真实阻断、用户批准或真机门。

复用提示词：

~~~text
仅在设计审查已触发时，作为非作者、只读 critic 独立审原目标/判据、批准范围、diff和仍需判断的未关闭项，不用作者自检替代判断。
按当前阶段与受影响合同检查；只因具体疑点扩读，不全量复读规则或聊天。
从真实调用者用法核批准职责与行为边界，再判断机制必要性；旧断言/工具细节不自动成为合同。
不默认逐格审核TSV；只追与本批合同/消费者/后果有关的行，普通代码/测试审查和机械核对沿原职责处理。
按当前阶段核可观察、可重放证据及证明边界；保留批准的结构/资源合同，不以“用户看不到”删约束。
问题须有依据、本批后果和关闭条件；建议不阻塞，关闭不绑定唯一修法。
明确需复审或可由Lead按原指定证据核对的项；后者核对关闭后不另求最终PASS，纯状态同步不把无实质问题的设计结论改成CHANGES_REQUIRED。
未覆盖的实现/运行/真机结论保持未覆盖，不能用设计结论代替。
~~~
