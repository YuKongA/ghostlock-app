## 0. 第一审查门：在保留批准职责的前提下简化（v0.5）

`design-critic` 先核对已批准目标、职责和本批缺口，再比较保持同一合同的直接方案，最后审机制自洽。没有用户价值不值得做；机制少也不自动正确。只有保持相同批准行为、成功含义、失败/资源终态与依赖边界的方案，才参与复杂度比较。

### 0.1 默认选择

- 从**已批准产品职责、本批承诺、当前缺口与失败模式**出发；caller 是实现证据，不是需求来源。“以后可能需要”不能单独证明今天应增加机制；已明确指定但尚未实现的职责也不因 caller 缺失自动失效。
- 先写出不增加新机制的 direct solution。提案若选择更复杂方案，举证责任在提案者：必须说明 direct solution 无法满足的具体现有判据，而不是只写“更通用”“更安全”“方便以后扩展”。
- 先确定职责与 owner，再在保持它们的可行方案中优先具体类型和直接调用。单 caller、单方法只提示检查转发成本，不证明职责可删。新增接口/中间层须对应真实平台或所有权边界、当前复用，或已批准且本批需要的变化轴；保留已批准职责不等于提前实现全部未来能力。
- 测试便利性不能单独证明生产抽象有必要；优先在已经存在的平台/副作用边界放置 test seam。
- 提议删除/绕开组件时，区分“能力已取消”“能力未实现/未接线”“实现重复”。删除能力需取消依据；删除实现需具名新 owner 承接对应行为与失败合同。源码不可达、类数减少或测试删完均不单独关闭产品项。纠正及临时指令的执行口径只引用 [E-REVIEW-RULE-004/§2](../../AGENTS.md#agents-change)。

### 0.2 阻断形态

下列形态触发必要性核查，不自动证明可以删除。审查者先定位受影响职责及本批后果，再提出保持同一合同的删除/合并候选；简化若转移已裁定 owner 或改变成功含义，应按变更提案处理，不能当成必须执行的“修法”。满足 §3.1 的阻断条件后才阻断：

1. 同一有序数据流存在两层及以上queue、sequence或drainer，但各层没有不同的owner、背压合同与独立终结点。
2. 上层与下层各维护一份表达同一生命周期的状态机，或用claim/abandon/timeout补偿本可由单一owner直接管理的资源。
3. interface/adapter/executor/registry/converter只转发一次调用，既不隔离真实边界，也不消除caller分支或重复实现。
4. 为尚不存在的backend、CLI、平台、provider或第三个实现预建公共合同、配置项、兼容层或动态发现机制。
5. 用timeout、重试、后台monitor或额外worker修补所有权不清；能先明确owner与终结顺序时，必须先简化所有权。
6. 新机制带来的类型、状态、并发边、测试矩阵与文档责任多于它删除的重复/分支，却没有有依据的当前收益或风险降低说明。

### 0.3 审查输出的首项

首轮设计审查在具体 finding 之前回答以下五项，可链接设计者已有说明；复审只更新发生变化的项，不重填模板。纯规则、文字或证据修订不适用的机制计数标明不适用，不虚构 caller：

| 项 | 必须回答 |
|---|---|
| 当前需求与本批缺口 | 用户可见的完成结果、批准职责/owner、本批交付分别是什么；caller 已存在还是入口尚未接线；链接已有目标与缺口即可 |
| direct solution | 沿真实输入→执行→用户结果链确定每段 owner；在保留批准行为、成功含义和失败/资源终态的前提下，最少机制如何完成 |
| 新增机制 | 新增多少interface/queue/worker/state/timeout/converter |
| 删除机制 | 同批删除哪条重复实现；原职责被谁承接或由何批准取消；未完成能力如何继续保留 |
| 复杂度差额 | 只在合同等价的方案之间比较 owner、queue、state、异步边界及验证成本；不以删职责来凑减少量 |

审查者不得因为复杂方案已经写得很完整，就把“继续补状态、补超时、补测试”当成默认修法；必须先判断是否应当删掉制造问题的那一层。该门只约束**无必要复杂度**，不允许以“简化”为名删除真实失败处理、资源终结、证据或已批准产品行为。

### 0.4 滚动细化：需求记录不等于本批承诺

在**现有唯一活动计划**的“目标与约束/进度”内区分以下三种范围；不新建 backlog 系统、审批角色或逐需求附件。已有独立需求清单保留其权威，只链接，不复制或擅改。

| 范围 | 记录到什么程度 | 何时进入当前批次 |
|---|---|---|
| 本批承诺 | 已批准目标、必要依赖、改动范围、验收条件 | 沿用现有 S/M/L 批准权限；实现前足够明确 |
| 后续需求 | 用户目标/来源、已知约束、待分析问题、owner 与重访触发 | 相关性/依赖分析、验收可说明且获原权限批准后纳入 |
| 待裁定 | 影响当前承诺的歧义或取舍及最小问题 | 只暂停受影响决策；不将未知自动当作本批实现任务 |

- **近细远粗**：前期侦查、需求被认可、写在同一计划，均不自动授权本批实现。后续需求不预写逐符号 TSV、不冻结完整状态机、不为假想接口建立抽象；不是遗忘、取消或完成。
- **纳入前只问实际依赖**：当前目标不实现它是否仍能独立验收？若能，留在后续；若不能，指出数据/合同/资源/安全依赖并把最小必要部分纳入，范围扩大仍需原权限批准。用户明确要求同批时不能自行延期，遇到不可行冲突一次说明并请求裁定。
- **已知未来约束现在评估**：后续已批准目标若影响当前难以逆转的接口、安全或容量选择，先做必要影响分析或最小可行性调查；不因此提前实现整个后续需求。未知但关键的依赖按 §3.1 处理。
- **承诺变更受控**：既有本批承诺不得悄悄重标为后续以躲过 gate；移出须记录批准、影响和重访触发。规范更新本身不改现有产品进度、既有承诺或真机欠账；旧计划仅在下一次实际触及时分类，不发动全库重写。
- **只细化即将实施的批次**：前批验收后，依据新证据细化下一批；同一批只解决一类目标及必要闭包。后续条目只作需求记录，不算本批未完成交付项。若当前 gate 无法判定而尚未实现，修正边界/补足设计，不先写未分析充分的生产代码来换取审核通过。

依据：教材 §4.2 需求基线与变更、§5.2 策划逐步细化、§7.1 设计贯穿开发；这是原 Explore→Design→Implement→Verify 内的范围规则，不是新增生命周期。

### 0.5 纠偏如何改变下一动作（复用原目标、进度与验证矩阵）

这不是新阶段或必填报告。仅在相关情形出现时，把下面的最小信息写回原条目；已有信息可直接引用。复盘不能只增加“更谨慎”要求，必须能解释下一次为何会采取不同动作。

| 触发／原失误机制 | 当前动作与责任落点 | 关闭或停止条件 |
|---|---|---|
| 重新划 owner、删除/合并机制；先按现存类设计，偏离用户结果 | 设计者从用户结果反推真实执行链，只在现有 owner/差异说明标清保留、转移、取消；critic 先核合同等价，再比较复杂度（§0.1–§0.3） | 批准职责无悬空、无双 owner；转移有依据。缺接线不等于能力取消，也不因清理旧实现勾选产品完成 |
| 同一计划里混入弱依赖需求，或为不可用旧连接预建兼容 | 依 §0.4 问“不做它，本批是否仍可验收”；兼容只服务已存在且须支持的调用者/数据或明确合同。具名纵向使用者优先验证技术选择，不迁移未获批的所有 backend | 必要依赖按最小闭包纳入；其余留原后续项。已批准当前承诺不擅自移出；合理长期目标不被删掉 |
| 用户纠正后旧指令仍被下批/子智能体读到 | 由当前执行者按 AGENTS §2 将替代关系落到直接消费的权威条款、当前入口及受影响委派；只复核这条依赖链 | 下一动作读到新裁定；失效方向停止。已定选择不因偏好重审；新的事实风险仍须报告，但不自动改方案 |
| 反复侦查、SHA、换环境或评审，却没有决策收益 | 执行者先说明本次检查会区分哪个未知及各结果如何改变下一步；critic 复用输入和关闭项。证据足够就交付，停止条件按 AGENTS §2 | 未知被回答或已有证据足够即停；无信息重复不继续。既定概率/时序验证所需重复保留，不用此规则逃避真实门 |
| UI 反馈反复出现，或把局部 PASS 当最终完成 | 在原判据上写明场景/前提、要观察的行为与匹配证据；视觉问题看对应画面/交互，结果问题看该层合同，不用编译或源码变化代替 | 对应反馈被观察结果关闭，或明确仍未解决；证据只关闭匹配层级，未覆盖部分继续未完成 |
| 紧急插入、停止规划、暂缓验证让长期目标或欠账丢失 | 沿用 AGENTS §2 的指令有效范围；现有进度位置保留本次允许动作、暂缓项、原恢复触发。交接引用这些指针，不抄全聊天 | 只交付获准动作；NOT_RUN 不变绿，停止项不自动重启。没有明确后续授权时不顺推下一批 |

上述表是对本项目反思的裁剪：参考 [Google SRE 复盘](https://sre.google/sre-book/postmortem-culture/)把注意力放在促成错误的条件与预防动作，而非责备个人；参考 [NASA 需求检查](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)的目标追溯、适当层级与可验证性；参考 [Google 审核内容](https://google.github.io/eng-practices/review/reviewer/looking-for.html)对设计、用户行为和过度设计的区分。不导入独立复盘系统、会议、量化打分或新的批准门。

## 1. 原则清单 v0.5

### A. 简并与去冗

<a id="review-a1"></a>

- **A1 同一事实只写一处**：按 [R1：单一权威](engineering-rules.md#r1) 检查重复表述；本文是审查入口，不另定一套权威规则。
- **A2 取代而非叠加**：新版本取代旧版本并划掉保留沿革，不得并列两套口径。（[R27：取代制](engineering-rules.md#r27)；旧 requirements/Q10 仅作沿革）
- **A3 完整与内聚**：文档不设字节、页数或篇幅硬上限；仍须短、直接、一处权威，并按职责/读者/权威边界拆分；不得为凑体量删除判据或证据。（[R30](engineering-rules.md#r30)）
- **A4 一个概念一个名字**：同一结构出现两个名字即视同缺陷，必须合并或明示同源（`= 原名` + `static_assert`）。

### B. 单一权威与一处读取

<a id="review-b1"></a>

- **B1 每事实一处权威**：旧号保留为 [A1：单一权威检查](#review-a1) 的入口；生成/对拍要求仍由 [R1](engineering-rules.md#r1) 定义，理论说明见 [E-REVIEW-RULE-003/§3](design-philosophy.md#philosophy-authority)。

<a id="review-b2"></a>

- **B2 一处读取**：任何数据只有一条读取路径；若并存 ⇒ 同批**逐值等价对拍**且声明仅作回退。（[R2](engineering-rules.md#r2)；本项由真实事故设立：载体/声明双读取路径曾使导出 `.bin` 静默丢队列）
- **B3 一处权威图**：一个结构只保留一处权威图，其它文档链接它，不重复画。（AGENTS 文档约定）

### C. 最小化与必要性

- **C1 最小改动**：只碰设计列出的文件；未列入改动清单的代码即冻结。（design-philosophy §5）

<a id="review-c2"></a>

- **C2 当前变化轴优先（v0.3 取代旧 C2）**：只有当前已有两个实现/consumer，或用户已批准且同批交付的第二变化轴，才要求写扩展点。禁止为假想的 op/backend/route/landing/执行器/脚本类型预建结构；未来需求出现时再按当时证据重构。旧 C2“每个新结构都必须预留扩展点”因会奖励投机性抽象而失效。
- **C3 成本权衡（用户口径 2026-10-07）**：**编译期收益必须与工程成本权衡；当编译期/静态方案的工程成本超过更灵活方案时，让路**。禁止只写「更安全」「更符合原则」——必须给 CBN（§2）。
- **C4 不做无收益抽象**：抽象应隔离当前真实变化、平台或所有权边界，或消除已有重复；登记远期需求不构成预建扩展点的理由。
- **C5 临时物零容忍**：临时开关/旁路同批登记并同批移除。（项目裁定；AGENTS §2/§3；[R13](engineering-rules.md#r13)/R23。教材 §6.2 讲抽象与模块化，不是本规则来源）

### D. 可验证性（**D1 为准**）

<a id="review-rule-d1"></a>

- **D1 判据形式 = 需求场景 + 等价类/边界 + 按风险选择白盒覆盖**（**取代** AGENTS「守卫/断言必须证明能失败」与 `engineering-rules.md` **[R10](engineering-rules.md#r10)**）：
  - **黑盒**：外部可观测行为（命令行退出码/输出、wire 文档字节、日志行、标记文件）；
  - **白盒**：内部结构（单元测试、`static_assert`、编译期表断言、层表/账本）；
  - 覆盖当前需求的正常/异常场景、有效/无效等价类及相关边界（0/1/MAX、空、超限、非法组合等）；边界是补充，不排除普通合法输入；白盒按风险选择分支、条件或路径覆盖；
  - 复用已有有效用例，一例可覆盖多项需求；不可达用例可排除，但须有前提/不变量依据，不以主观“不可能”跳过真实失败模式；
  - **不再要求**为守卫/断言做**造错（证伪）实验**——该要求自 v0.2 起为**可选手段**而非门槛。
- **D2 判据分层**：离线可重复 / native 构建 / 真机，各有一处入口与记录。（[R14](engineering-rules.md#r14)）

<a id="review-d3"></a>

- **D3 分层证据不越界**：纯逻辑、解析和状态转换可由对应层测试验证；设备依赖行为、攻击关键路径与端到端成功仍须目标真机证据，AVD/host/静态检查不替代。冷机、固定 CPU 对、单 route、KernelSU 未加载、产物身份及日志归档等沿用 AGENTS §8；未过真机的新 profile 不标 supported。设计批准不等于实现完成或设备 PASS。（[R15](engineering-rules.md#r15)；教材 §8.14–8.17）
- **D4 产物身份 + 新鲜度**：APK/ELF/profile/golden 等身份敏感产物保留路径/字节/mtime/sha；观测与代码矛盾时先核新鲜度。普通审核按 G4 标识输入，不反复给未变化文档算 hash。（[R16](engineering-rules.md#r16)；AGENTS §2）
- **D5 失败数读 XML 全量**，不看控制台尾部；报告给三桶计数。（[R17](engineering-rules.md#r17)）
- **D6 具名诊断是契约**：阶段/原因标识发布后不得改义。（[R11](engineering-rules.md#r11)）
- **D7 fail-closed**：失败不得降级继续（无默认继续/自动换路/自动重试）。（[R12](engineering-rules.md#r12)）

### E. 结构约束与安全

<a id="review-e1"></a>

- **E1 边界与耦合**：层间优先显式数据合同；禁止窥探内部结构、以共享可变全局或下层读取上层内部标志驱动行为。显式协议命令、调度和回调不因含控制信息自动违规，须审合同与依赖方向；项目更严限制应指明适用边界和理由，不冒称教材全面禁止。（[R3](engineering-rules.md#r3)；教材 §6.3）

<a id="review-e2"></a>

- **E2 功能内聚**：一个可说明的职责，不等于函数/类物理不可再拆。拆分须同时评价接口、耦合与集成成本；不以模块数量或一句话长度判通过。（[R4](engineering-rules.md#r4)；教材 §6.2–6.3）
- **E3 编译期锁定**：组合→步骤集→终端在编译期绑定，运行期只做声明符合性检查。（[R6](engineering-rules.md#r6)）
- **E4 PI 窗口约束（实证版）**：**白名单/禁项以 [pi-window-constraints](../analysis/pi-window-constraints.md) 为准（口径 = `inside PI`：约束只覆盖 PI 内那几段，PI 之后可打印）** —— 实测死因 = 窗口内 `sched_setattr`（改 nice / SCHED_BATCH）进入内核 PI 链（`__do_sys_sched_setattr` → `__sched_scheduler` → `rt_mutex_adjust_pi`，见 device-gate `20260922-2231-CPP12x/CPP12s-*-panic`）。因此：**禁 `sched_setattr` / `setpriority` / `nice` 及任何会进入 `rt_mutex_adjust_pi` 的调用**；并保留**禁堆分配 / 禁间接分派 / 禁首次触页**（防御性条款）。窗口外允许虚接口（gate/计划/配置构造/终端交接）。

> **沿革**：原 E4 表述为「PI 窗口内禁间接分派/分配/首次触碰新页」（由 ADR-0001:183、ADR-0004:188-189、`route_lifecycle.hpp:9-11` 推下）—— 该理论条款**覆盖不到实测死因**；2026-10-08 按 device-gate 记录改写为「白名单 + 禁项」，原文保留于本行。

<a id="review-e5"></a>

- **E5 双读取路径 = 高危形态**：本仓 M5 事故的检查入口；判据统一引用 [B2：一处读取](#review-b2)，不重复定义。
- **E7 共享工作树保护（硬规则，2026-10-07 事故后立）**：任何 teammate **不得**执行会改变共享工作树的 git 命令（`checkout/restore/stash/reset/clean`），**也不得**等效写回（`git show REV:path > path`）；历史比较只用只读形式（`git show REV:path` 不重定向、`git diff REV -- path`、`git log`）。
- **E8 写回完整性（硬规则，同源）**：**禁止分片读 + 全文写回**——`read(offset/limit)` 只给窗口、`write` 整体替换；读须整份读（或确认读到 `totalLines`）或改用定点 `edit`。若确需整份写回，**写回前后核对字节数与行数**并在报告给出。

<a id="review-e6"></a>

- **E6 守卫可失败**：旧号保留为 [D1：验证覆盖](#review-rule-d1) 的取代指针；造错仍为可选加强手段（尤其是 vacuous 断言风险场景）。

### F. 记录与沿革

- **F1 不删历史**：被推翻的提法划掉保留 + 一行理由；用户裁决必须记录。（AGENTS 沿革条款）
- **F2 技术债预判（v0.3 收窄）**：只记录当前方案已经明确产生的债、owner与偿还触发；未来可能新增的功能只作为触发条件，不授权今天预建扩展机制。登记到 decisions（或专门的技术债文件）。
- **F3 强制确认须核沿革与技术债**：用户强制越权时，审查者必须核对「沿革记录 + 技术债登记」是否都在；缺一即视为未完成。
- **F4 决策可检索**：时间 · 原则版本 · 总判 · 阻断数，一行一条。（design-philosophy §9）

### G. 事实与证据

- **G1 每条结论带依据**：`file:line` 或原则/R 编号；明确区分教材原则、项目裁定和个人建议。阻断还须满足 §3 的阶段相关性与后果举证，不以规则编号代替因果说明。
- **G2 禁止外部计划引用与未定义标签**：标签必须能在本族文档中找到定义（否则先补「标签 → 来源」表）。
- **G3 未核实项显式标注**：不得把推测写成事实（写「未核实」并给核实路径）。

<a id="review-g4"></a>

- **G4 审查前提 = 可识别输入**：记录 HEAD、时间、目标文件和本轮 diff；未提交修改属于输入，不能仅以 HEAD 代表工作树。只为本批实际改变的关键文件或身份敏感产物保留必要 hash。相关 writer 停手后评审；审查中输入变化，只使受影响结论失效，按 §3 增量复审，不因无关文件写入全量重跑。

## 2. CBN（成本权衡依据）规范

**强制适用**：提案拒绝 §0.1 的 direct solution、保留/新增 §0.2 的复杂机制，或评审双方对复杂方案的当前收益存在真实争议时。**禁止只写「更安全」**。

**不重复适用**：已证明合同等价，且 §0.3 或已有设计已充分说明当前必要性、成本与风险时，直接引用，不要求 owner、queue、state、async wait 各项计数同时下降。仅为尚未解决的真实取舍补 CBN，不重复已有充分论证；不为凑模板制造第二备选、虚构收益数字或翻转条件。CBN 是复杂方案的举证工具，不是每次保留/合并/拆分都必须填写的第二套流程。

| 字段 | 必填内容 |
|---|---|
| **决策点** | 一句话：在哪个结构/哪一层做选择 |
| **备选** | 比较真实可行的方案，优先包含 direct solution；只有一个可行方案时说明其余被何约束排除，不凑备选 |
| **收益** | 有测量用测量，有估算给依据/区间；定性风险说明因果与不确定性，不强制凑数字 |
| **成本** | 当前工程量、认知/运行/验证成本；已知变化轴才评估边际成本，不枚举假想功能 |
| **翻转条件** | 什么情况下**必须改选**另一方案（可判定，不写「视情况」） |
| **结论** | 选定方案 + 一句为何 |

- **决策规则**：先满足当前需求与适用约束，再比较有依据的总成本和风险；不默认更动态、更静态或机制更少就更优。C3 的成本权衡仍保留。
- **刻度**：关键取舍未经论证才需补证；数字缺失或备选数量不足本身不是阻断。已有 §0.3 的论证直接引用，不再复制一份。

## 3. 审查执行与产出（沿用原岗位，不增加审批层）

### 3.1 先判阶段与影响，再判阻断

每轮先确定“本批承诺、当前阶段、要过哪个 gate”。阻断须同时给出：**适用要求 + 当前阶段 + 证据位置 + 对本批验收/安全/关键可行性的具体后果或依赖链 + 关闭条件**。规则编号、模板缺项、工具报红或“尚未实现”本身不足以证明阻断；信息缺失写明待确认事实，不当作已证实缺陷。关键缺证确实使当前决策无法成立时，可阻断该决策并指明最小补证。

| 当前阶段 | 应审证据 | 不提前索取 |
|---|---|---|
| 需求收集/前期侦查 | 用户目标、已知约束、未知问题、与当前批次的依赖 | 完整设计、逐符号 TSV、成套测试及生产实现 |
| 设计批准 | 当前需求→设计→验收映射、关键合同/owner、可行性、验证方法和预期结果 | 尚未进入实现阶段的完整 test source、生成结果或运行 PASS |
| 实现交付/验证 | 当前约定的实现、测试、必要工具/manifest、执行结果及身份 | 弱相关后续需求的实现；与当前变更无关的历史工具债 |

- **关键可行性不能后移**：若当前设计依赖未经证实的平台能力、接口或资源条件，先以必要来源证据或最小实验回答该问题；实验不授权提前实现后续完整需求，仍遵守原有实验入口与变更纪律。
- **test/TSV 按用途判断**：测试、符号表或 manifest 若用于当前生成、构建、ABI/注册一致性、删除边界、身份或验收覆盖，其缺陷可以阻断相关 gate；仅作审计展示的格式、命名或远期符号清单不自动阻断业务设计。必须说明“哪项合同→谁消费→怎样影响本批”。
- **不以工具迁就取代产品设计**：生成器或检查器落后时，定位它与批准合同的差异；不为消除误报改变产品行为。需要修工具/fixture 的最小闭包仍同批处理；不删除有效测试、不放宽真实判据、不伪造 TSV/PASS。已有明确承诺的工具合同要变更，先按原权限批准。
- **设计者负责方案，critic 负责缺陷**：关闭条件写必须成立的性质，修法只作可选建议。critic 建议增加 owner/queue/state/worker 时，也须重新证明必要性，不强制唯一实现。
- **先按证据所在层关闭**：复用已有验证矩阵，写清本条证据证明的行为、运行前提及尚未证明的上层行为。raw uid 0、诊断 PASS、脚本 dispatch、Payload/Finish 结果与产品成功按各自已批准合同判断；下层通过不自动关闭上层。本批只覆盖其改变的链段及必要集成，不每批重跑无关整条产品链。
- **反馈对应可观察判据**：用户指出 badge、间距、对齐或保存闪退时，把指定场景、皮肤/环境和可见现象补入原缺陷的关闭条件，并核对相应运行结果；编译绿、修改了源码或解释设计意图不等于修好。新细节若改变原产品要求则按范围变更处理，不悄悄增加当前承诺。

<a id="review-incremental"></a>

### 3.2 增量复审与上下文节约

1. **输入包复用现有材料**：本轮阶段/唯一交付物、当前需求/owner与判据指针、直接相关的最新裁定及取代关系、目标章节/文件、相对上轮 diff、未关闭 finding 及回应、适用验证欠账/恢复触发。只引用本轮会消费的已有位置，不另建平行台账、复制完整聊天史或全文计划。
2. **首轮完整覆盖适用维度**：需求完整性、可行性、简化、接口/资源/失败路径、验证策略；复用原需求/验证矩阵，标明已覆盖、缺口、不适用及理由。零 finding 不代表未经检查的维度已通过。
3. **复审 = diff + 影响范围 + 未关闭项**：从变更追到受影响合同、调用者和判据，而非仅看修改行；未变化且依据仍有效的结论直接复用。规范变化、依赖变化或新证据推翻旧结论可重开，须给新理由；首轮漏审后发现的真实风险也须报告，不隐瞒以压低轮数。
4. **同岗保留简短状态**：稳定 finding ID、关闭条件、状态、证据指针、当前适用范围；复审只输出新增/仍开放项和关闭 ID 的短依据，不重播旧报告。独立第二视角只用于实质争议或跨领域风险，不每轮无条件全量并行。
5. **读取与工具有目的**：每次扩展读取说明要解决什么判断；机械检查优先复用现有工具，工具执行由负责者提供结果，critic 保持只读/不跑门禁。未变化输入不重复扫描、算 hash、轮询；缺失信息只问影响下一决策的最小问题。
6. **结束条件**：当前适用维度已覆盖、无未关闭阻断且结论边界清楚即结束；不为“再找一个问题”继续。节约 token 不设文档/报告长度或审核轮数硬上限，不删证据、不降低验收；可利用已有日志观察重复读取、重开原因与漏审，暂无数据时不声称节省百分比。

### 3.3 输出与关闭

| 编号 | 严重度 | 阶段/位置 | 问题、证据与本批后果 | 关闭条件（可另附建议修法） | 依据 |
|---|---|---|---|---|---|
| E-REVIEW-RULE-001/问题01（格式示例，非已登记问题） | 阻断/重要/建议 | gate + file:line | 指明影响的当前需求或合同及依赖 | 可核对性质，不强制唯一实现 | 教材/项目裁定/建议分别标明 |

- 问题代号继承被审对象的根，按[文档规范](documentation-standards.md#engineering-identifiers)跨报告连续唯一；旧 finding 保留完整来源，不再复用规则 C1。报告标题与聊天交接同时给中文主题，不让用户猜字母。
- 输入包是已有材料的链接，不是副本目录；普通文档校验直接运行必要命令，结果进已有审核记录，不新建验证脚本/备份包/回滚演练（AGENTS §6）。
- 首轮附 §0.3 与需求覆盖指针；复审只附变更及影响、OPEN/新增 finding、CLOSED ID 短依据。
- **总判**：设计阶段为“可进批准 gate”或“仍需修订（列当前阻断）”；其他阶段明确该阶段与结论。关键输入缺失写明暂未覆盖范围和所需补证，不把资料缺失伪装成实现失败。
- **阻断项未关闭不得过其对应 gate**；重要项若不影响当前准出可登记 owner/处理触发，建议不阻塞。跨批需求依 §0.4 处理，不因文档共存而扩大 gate。
- 必附“验证了什么 / 没验证什么”；设计通过、源码交付、测试通过、真机验收分开报告。关闭项给对应判据与证据，不能仅写“已修改”；暂缓验证继续指向原欠账，不复制第二份报告。设计者逐条回应；接受、反驳或延期都保留理由，越权沿革仍按 F3。

复用提示词：

~~~text

先定位唯一交付物、批准职责/owner、当前缺口和最新有效裁定；引用已有位置。
简化方案先保持行为、成功含义和资源终态，再比较机制数量；未接线不等于可删。

记录需求不等于承诺实现；设计可批准不等于 test/TSV/运行结果已经交付。
~~~

- **v0.1**（2026-10-07 早）：判据含「造错必失败 / 证伪实验」**通用要求**（承 AGENTS 验证门槛 + `engineering-rules.md` R10）。
- **v0.2**（2026-10-07 用户裁定）：
  1. **D1 为准**：判据改为**黑盒/白盒 + 极端输入值**；**删除证伪实验的通用要求**（AGENTS 同条与 R10 保留原文、标注为**可选手段**）；「不可能发生」的用例不测。

  1. 把“严防过度设计”提升为 design-critic 的第一审查门；先比较 direct solution，再检查复杂方案的内部自洽。
  2. 明确双queue/重复状态机/纯转发层/假想扩展点/以timeout修补owner为默认阻断形态。
  3. C2 从“每个结构必须预留扩展点”改为“只服务当前或已批准同批变化轴”；F2 不再要求枚举假想功能，也不授权预建机制。
