# CVE-2026-43499 select_stack — API35 AVD result

- Time: 2026-10-20 18:26 America/Toronto
- Device: GhostLock_6_6 (Pixel_5 AVD) - Android 15, kernel 6.6.30
- Test: com.ghostlock.app.NativeSelectStackInstrumentedTest
- Result: test PASS (JNI edge), route not successful

## Observed

Before waiter_tid atomic fix:

`NativeSelectStackResult(statusCode=0, statusStep=61, attempts=1, calls=1, successes=0, waiterLock=0, waiterPark=-1, waiterParkErrno=110, consumerSetattr=-1, consumerSetattrErrno=3)`

After the atomic `waiter_tid` fix and a rebuilt APK:

`NativeSelectStackResult(statusCode=0, statusStep=61, attempts=1, calls=1, successes=0, waiterLock=0, waiterPark=-1, waiterParkErrno=110, consumerSetattr=-1, consumerSetattrErrno=3, requeueResult=-1, requeueErrno=22)`

After exposing the actual race result and matching the reference CMP_REQUEUE_PI arguments (`val=1`, `nr_requeue=1`, `val3=0`):

`raceLock=0, raceRequeue=0, raceOutcome=5 (Refused), waiterPark=-1/ETIMEDOUT, successes=0`.

The route now reaches the real requeue call, but it moves **zero** waiters. The waiter is not in the kernel queue at requeue time, despite `waiter_waiting`; consumer ESRCH also reappeared intermittently. This is a sequencing/queue-insertion problem, not an extractor problem.

A target pre-lock before `run_actors` was tried and hung the AVD test (>10 min); it was reverted.

A dedicated owner thread was then added: it locks target, waits for waiter_ready, locks chain, and releases after stop. The deadlock was fixed (owner now waits for waiter_ready before chain), but the result is unchanged: `requeue=0`, `successes=0`, waiter ETIMEDOUT. The owner thread is not yet enough to put the waiter in the requeue queue.

A requeue retry loop (200 x 10 ms, while the waiter is still inside its bounded park) also returned 0 every time. The waiter is not observable in the kernel queue for the whole park window.

A second, self-contained select route was ported from the reference snapshot (`select_stack_route_legacy.cpp`) and exposed as `NativeSelectLegacyJni`. AVD result with zero FakePage: `status=2, step=30, errno=0`; the legacy route also refuses at its fake-page guard. No success claim.

Latest current-route diagnostic: at requeue time `targetOwnerWord=-2147479763` (owner holds target) and `waitWordValue=0`; `raceRequeue=0`. The test completed in ~0.1 s because the futex timeout was relative, not absolute.

After fixing the wait to an absolute CLOCK_MONOTONIC deadline, `waiterParkElapsedUs=2000851` (a real 2 s park). With CMP_REQUEUE_PI `val=1, nr_requeue=1, val3=0` it returns 0; with `val3=*target` it returns -1/EAGAIN(11). The waiter now really parks, but the requeue still does not match it.

## Meaning

The API35 extractor derives `pselect_waiter_shift=-2`, and the JNI route reaches the same failure shape as API33: `calls=1`, `successes=0`, waiter park ETIMEDOUT. This is not an extractor omission; the current test config/fake page is insufficient for a successful select route.

## Not proven

- select route success;
- page landing;
- uid=0.
