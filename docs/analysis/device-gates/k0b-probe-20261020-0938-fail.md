## 判读

- `wait=-110` 是 `ETIMEDOUT`：等待者确实 park 过，但在 200 ms 内没有被 requeue 醒。
- `requeue=-22` 是 `EINVAL`：把 `FUTEX_CMP_REQUEUE_PI` 的 `val` 从 1 改成 0 后参数不合法；C++ 侧当前约定是 `val=1` 且 requeue 前把 chain 字置 1。
- `completed=true` 只表示三条线程 join 完成，不是 PI 成功；`page-write=false`、`root=false`。
- 早先一轮（未记录 `k0b-wait`）为 `requeue=0`，同样没有搬动等待者。

## 结论

**K0b 未过，不进入 K3；不标 supported。** 需要下一步 debug：

1. 增加对 chain/wait 字当前值的可观测读取（或等价的 syscall 级读回），确认 park 条件与 requeue 的 `val`/`val3`。
2. 按 C++ 的 chain 预置/等待字分离修正顺序，再跑同一 AVD；连续失败 2 次即停。
3. 只有 `requeue` 返回非 0 且 `wait` 不再 `ETIMEDOUT`，才讨论页写入与 K4。

## 边界

- 该 AVD 不是物理设备；此记录只证明 per-syscall JNI + Kotlin actors 能在 Android 13 上跑通，不证明真机 PI 窗口。
- 未改生产成功判据；`KtStepEngine` 仍要求 victim uid。
