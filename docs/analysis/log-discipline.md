# 后台/设备任务的日志纪律（2026-10-12 用户裁定 · 强制）

> 「以后你执行后台任务，要先输出完整的日志，然后再用grep截取你需要的」

## 规则（三步，顺序不得颠倒 ✓）

```
① **先落全量**：任务输出**不预先过滤** ⇒ `> /tmp/<task>.log 2>&1` ✓（stdout ＋ stderr 全收 ✓）
② **再完整输出**：先 `cat`／`tail -n +1` 把**整份**日志交出来 ✓（⇒ 至少给出总行数与全文 ✓）
③ **最后才 grep**：在**已落盘的全量**上截取 ✓ ⇒ 并**标明**是从哪份文件、按什么模式截的 ✓
```

## 为什么要这样（本会话的代价 ✓）

```
· 我此前惯用 `grep -oE "..." | head -N` **就地**过滤 ✗ ⇒ ⇒ **丢弃了上下文** ✗：
    · 第 105 轮：`park <- ret value=66` 与 `requeue <- ret value=0` 的**时间差 157 ms** 是
      **靠两次不同 grep 的拼合**才看出来的 ✗ ⇒ 若当时**先整份输出**，一眼即得 ✓✓
    · 第 96 轮：因为只看 `check`、未看 android 全量 ✗ ⇒ 三处编译错**延后一轮**才发现 ✗
    · 多次"读数不变"的结论，其实是**我的过滤式在变** ✗ ⇒ 不是数据在变 ✓
⇒ ⇒ **⇒ 过滤 = 不可逆的信息损失** ✗ ⇒ 先落全量再过滤 ⇒ 信息只损失**一次**且**可重查** ✓✓
```

## 落地（已生效 ✓）

```
· 设备：`adb shell ... > /tmp/<name>.txt 2>&1` ✓ ⇒ 先 `cat`／`wc -l` 全量 ✓ ⇒ 再 grep ✓
· 门禁：`make ... > /tmp/<name>.log 2>&1` ✓ ⇒ 先看全量（含尾部与失败计数 ✓）⇒ 再 grep `error:` ✓
· 设备内日志文件：`ghostlock.log` ✓ ⇒ 先 `cat`（或 `wc -l` ＋ 全文）⇒ 再 `grep -c` 计数 ✓
· 归档：全量日志**保留路径**并在归档里写明 ✓（⇒ 便于复核 ✓）
```
