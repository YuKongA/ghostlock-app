## 1. 需求（只用非实现语言表述）

### 1.1 项目性质（决定架构的第一性事实）
| # | 事实 | 架构含义 |
|---|---|---|
| N1 | **一次性现场工具**，非产品、非服务、非平台 | 不引入插件市场/多租户/热更新/ABI 兼容层；不为"将来可能要"设计 |
| N2 | 攻击链**时序敏感且不可重复**（PI-futex 竞争；失败可能 panic） | 一切可能失败的前置校验必须**前移到不可逆步骤之前**；不可逆段只做一件事 |
| N3 | 只在**精确匹配的单一内核**上工作（`uname -r` 不等即拒绝） | 配置是**资产**而非参数；运行期无"配置发现"逻辑 |
| N4 | 三语言三平台（Kotlin/Compose 应用、C++23 native 运行时、Rust 离线提取器） | 层间只允许**声明式制品**；禁止跨语言代码级耦合 |
| N5 | **真机是唯一判据** | "证据"是一等交付物；离线相似物（反汇编一致性等）只能作诊断 |
| N6 | 单开发者兼操作者，研究级 | 部件数量最小化；每个部件职责单一 |
| N7 | 运行环境无调试器、无网络、随时可能死机 | 具名诊断必须**在二进制里**；失败必须能定位到阶段 |
| N8 | 授权设备、合规边界明确 | 仅对本机授权设备；密钥/SPI/端口永不落文档 |

### 1.2 用户非实现层要求（功能与约束）
- **选择面**：只能展示 / 选择**配置已声明 available** 的路径（未声明的必须不可见或置灰）。
- **呈现结构**：执行组合以**子菜单**展开；层级为**树状**：backend → route → handoff。
- **路径本地化**：组合/入口文案一律本地化，不出现内部 token 直译。
- **校验口径**：必需项**按声明路径**判定（声明 43499 才要求 43499 的必需项）。
- **配置资产**：general profile 恰为 `<x.xx>-android<NN>-general.conf` 8 份。
- **UI 组件**：使用 **Miuix 原生**组件及其自带 Defaults；**禁止手调基本数据（间距像素等）**，一律由 Compose 自动排版。
- **选择器 UI**：整体重写（不沿用旧交互）。
- **插件/payload**：冻结；handoff 已解冻并纳入 available。
- **实验方式**：禁止新增 CLI/旁路；实验必须走**生产路径**（参数化/去限制，而非加开关）。
- **不新增硬要求**；不引入图像识别类高成本依赖。
- **构建产物**：必须在仓库内真实 `build/`，禁止任何符号/硬链接；产物可丢弃。
- **文档**：拆分 analysis / plan / archive；主计划自包含（不靠 .md 链接）。
- **提交**：未经要求不 commit。

### 1.3 质量属性优先级（冲突时按此序）
1. **正确性（fail-closed）** 2. **可判据性（真机证据可复现）** 3. **可诊断性（具名失败）**
4. **可维护性（低耦合优先）** 5. 可移植性（仅限新 release 适配） 6. 性能（只在攻击链内是硬指标）

## 2. 概要设计（架构设计）

### 2.1 体系结构风格
**四层 + 两个横切面**，层间**只经声明式接口**通信（教程 §6.1 要求"各层可独立升级/替换"）：

| 层 | 职责（业务语义） | 允许依赖 | 产物/接口 |
|---|---|---|---|
| **A 表示层** Presentation | 呈现选择面、收集选择、展示结果与证据入口 | 只依赖 B 的**只读视图接口** | Compose UI |
| **B 业务层** Business | 装配：资产加载 → 合并 → **声明门禁** → 归一 → 发射 wire 文档 | 只依赖 C 的**资产格式** | HOCON 资产 + GLKv3 文档 |
| **C 执行层** Execution | 在匹配内核上执行**唯一**攻击链并汇报阶段 | 只依赖 B 的**wire 文档** | 阶段化 status/日志 |
| **D 数据层** Data | ① profile 资产 ② 设备事实台账（release/KMI/ABI 常量） | 无 | 文件 + 表 |
| **X1 契约面** Contract（横切） | 词汇与组合的**唯一权威**（kind/route/stepset/terminal/queue 语义） | 无（最底层，可 host 编译） | 目录表 + 生成的 manifest |
| **X2 证据面** Evidence（横切） | 真机门禁记录的生成与归档 | 只读 C 的输出 | 门禁记录 + 原始日志 |

**风格判据**：这是"**声明驱动 + 编译期锁定 + 单向数据流**"的分层风格；不是插件式、不是微服务、不是事件驱动。

### 2.2 层次结构图（模块树，深度 4、扇出 ≤ 5；满足 §6.5 的 ≤7 约束）
```
System
├── A 表示层
│   ├── A1 选择面视图（树：backend → route → handoff；仅 available 可点）
│   ├── A2 状态视图（内核/设备/CPU 对/就绪度）
│   ├── A3 执行视图（阶段进度、结果、证据位置）
│   └── A4 UI 基元（Miuix 封装；无业务逻辑、无像素常量）
├── B 业务层
│   ├── B1 资产装载（内置 + 用户覆盖；只读）
│   ├── B2 合并与归一（唯一合并实现）
│   ├── B3 声明门禁（按声明路径校验必需项；未声明即拒绝）
│   ├── B4 选择权威读取（available → 选择面；**唯一读取路径**）
│   ├── B5 文档发射（wire 编码；唯一编码器）
│   └── B6 运行期剖面落盘（profile.conf/profile.bin：证据与复现）
├── C 执行层
│   ├── C1 文档解析与契约归一（唯一解析路径）
│   ├── C2 组合分派（编译期固定）
│   ├── C3 攻击阶段（race/waiter/payload/write/hook/trigger）
│   ├── C4 终极端（handoff：root child / umh forward …）
│   └── C5 阶段汇报与具名诊断
├── D 数据层
│   ├── D1 profile 资产（每 release 1 份 + general 8 份 + 公共/分 route）
│   ├── D2 设备事实台账（ABI 常量、KMI 表）
│   └── D3 LKM 载荷（按 KMI 分档）
└── X 横切
    ├── X1 契约目录（组合/词汇/stepset/queue 语义）
    ├── X2 生成的对拍清单（combination / vocabulary / stepset / lkm-kmi）
    └── X3 证据归档（device-gate）
```

### 2.3 模块独立性目标（教程 §6.3）
- **耦合**：层间**只允许数据耦合**（传"文档/资产/只读状态"）。
  - 禁止**公共耦合**：不新增可变全局；现有进程级 singleton 视为**既定例外**且只读。
  - 禁止**控制耦合**：下层不得读取"上层让我怎么做"的标志位；行为差异只能来自**数据（profile/文档）**。
  - 禁止**内容耦合**：无跳转、无跨模块内部结构窥探。
- **内聚**：每个模块追求**功能内聚**（一个模块 = 一个可命名功能，缺一不可）。
  - 明确拒绝**逻辑内聚**（"一个函数按参数干几种不同的事"）与**时间内聚**（"启动时顺手做的一堆事"）。
- **规模**：单文件目标 **200–400 行**（Hatton 最低错误密度区）；> 600 行必须拆分或给出理由。
- **矛盾时优先降耦合**（教程 §6.3 明确要求）。

### 2.4 关键机制（四条结构性机制，替代一切"约定"）
1. **单一权威**：每个事实只有一处权威（组合语义在契约面；可用性在 profile 声明；内核事实在台账）。其余皆为**派生**，且派生必须机器生成或对拍。
2. **一处读取**：任何数据只有**一条**读取路径。若确需第二条（如"载体"与"声明"），必须**同批**给出逐值等价对拍，且**声明只作回退**。
3. **编译期锁定**：组合 → 步骤集 → 终极端的关系在编译期绑定；运行期只做**声明符合性**检查，不做语义推断。
4. **fail-closed 三层失败**：解析失败 / 契约失败 / 执行失败，各自有**独立具名**诊断，且永不降级为"默认继续"。

### 2.5 数据设计
- **资产**：每 release 一份 profile；8 份 general（横切维度）；公共调参与分 route 调参分离。
- **wire**：单一文档格式（版本号与配置同号）；根标量 + owner 段；选择面以**队列对象**表达。
- **清单**：组合/词汇/步骤集/KMI 四张，**由权威生成**（不手抄），双侧逐字节对拍。
- **证据**：每次真机运行落一份"生效配置 + 送入字节 + 阶段日志"三件套。

### 2.6 运行设计（时序，单向）
```
启动 → 读内核事实 → 匹配 profile（不匹配即拒绝，无回退）
     → 装载/合并资产 → 声明门禁校验 → 构建"选择面视图"
     → 用户选择（仅 available）→ 归一为队列/route/终极端
     → 发射 wire 文档（并落盘三件套）
     → 执行层解析 → 契约归一 → 阶段化执行（不可逆段最小化）
     → 阶段汇报 → 成功则交接 → 证据归档
```

### 2.7 出错设计
- 三类阶段（read / backend / terminal）+ 契约类拒绝，**每条都有稳定具名标识**。
- 失败必须能回答三个问题：**哪一层、哪个输入、哪个判据**。
- 不做自动重试；不做"失败后换条路"（N2）。

### 2.8 界面设计（教程 §6.7）
- **唯一交互模型**：树（backend → route → handoff），叶子即"可执行组合"，未声明者不可点。
- 视觉与间距**全部交给组件与主题**；代码中不出现像素常量。
- 选择结果必须在入口处以人类可读摘要呈现（可核对）。
- 不呈现内部 token；不呈现无来源的数字。

## 3. 详细设计要点（交给程序员的约束，不含实现细节）
1. 模块边界 = 上述 A/B/C/D/X 的叶子；跨边界只传数据。
2. 每层入口函数数量最小化；禁止"万能控制器"（>600 行的 controller 视为架构缺陷）。
3. 诊断是**契约**：标识符一旦发布不得改义。
4. 写入一律原子（临时文件 + 替换）；任何"就地改写"视为缺陷。
5. 产物可丢弃：任何缓存/中间物都可在 clean 后重建。
6. 守卫必须证明**能失败**（否则不是守卫）。
7. 观察者不得污染被观察对象：UI 只读，执行层不回写配置。

## 4. 对照现有架构

### 4.1 结构性偏离（按严重度）
| # | 现状 | 目标 | 根因（架构级） |
|---|---|---|---|
| P1 | **同一事实多处描述**：组合语义同时存在于契约表、若干 manifest、AGENTS、UI 词表 | 单一权威 + 机器派生 | 缺"派生物"概念；靠人工同步 ⇒ **公共耦合** |
| P2 | **同一数据多条读取路径**：载体/声明、canonical 键名 vs wire 字面名 | 一处读取 + 同批对拍 | 无"读取路径唯一性"约束 ⇒ 本会话多数 bug 的直接来源 |
| P3 | **业务层过载**：解析 + 合并 + 门禁 + 发射 + 缓存集中在一个千行级控制器 | 拆为 B1–B6 六个功能内聚模块 | 逻辑内聚 + 时间内聚 |
| P4 | **文档体量超过代码**（docs ≈ 40k 行 vs app ≈ 15.6k 行；单篇 153 KB） | 规格唯一、分析只留"为何" | 把"过程记录"当"设计" ⇒ 判据与设计纠缠 |
| P5 | **历史层积**：过时 CLI、旧格式遗骸、注释冻结域到处可见 | 只保留一处沿革说明 | 缺"删除纪律" |
| P6 | **跨语言契约靠手抄**（部分已机器化） | 全部生成 + 对拍 | 手工同步不可验证 |
| P7 | **判据散落**：门禁记录数量巨大且互相引用 | 判据分层（离线/真机）+ 单一索引 | 证据未建模 |
| P8 | **单文件超限**（数百至千行） | 200–400 行目标 | 未按功能内聚切分 |

### 4.2 符合目标的部分（应保留并强化）
- 契约面作为**最底层可 host 编译**的词汇权威 ✓（方向正确）。
- **fail-closed** 与"未声明即拒绝"已在多处生效 ✓。
- 已出现**生成式对拍清单** ✓（组合/词汇/步骤集/KMI）⇒ 应推广为通则。
- **具名诊断**机制已进二进制 ✓（本会话多次直接命中）。
- 构建产物统一落仓库真实 `build/`、可 clean 重建 ✓。

### 4.3 本会话 bug 的架构解读（重要）
本会话反复出现的失败几乎都不是"实现错误"，而是 **P1/P2 的症状**：
1. 选择面既定"队列"又残留"token"语义 ⇒ 双语义并存。
2. 43284 与 43499 在**同一机制**上呈现不对称（一个有裸段，一个没有）⇒ 缺少"对称性"这一结构约束。
3. 运行期文档与导出文档走**两条装配链** ⇒ 同一事实两条路径。
4. 诊断"只在失败时打印"导致**观测盲区** ⇒ 观测设计未建模。
⇒ 结论：**先把 P1/P2 变成结构性约束，再谈功能**；否则同类缺陷会持续再生。

### 4.4 收敛方向（结构性，不含实现细节）
1. **契约面集中**：把"组合/词汇/步骤集/终极端/可用性"的语义收敛到唯一权威，其余一律生成。
2. **读取路径唯一化**：任何数据只留一条读取路径；必须并存的，同批给出对拍并把声明降为回退。
3. **业务层切分**：按 B1–B6 六个功能内聚模块重组，控制器退化为"编排"（≤ 200 行）。
4. **证据建模**：判据分"离线可重复"与"真机唯一"两类，各有一处索引；文档从"过程记录"回到"规格 + 为何"。
5. **删除纪律**：每次结构变更同批删除被取代物；只在一处保留沿革。

## 5. 结论与优先级
**架构目标一句话**：*单一权威的声明 → 唯一读取路径的装配 → 最小不可逆段的执行 → 可复现的证据*。

优先级（先做结构，后做功能）：
1. P2 读取路径唯一化（收益最大：直接消灭本会话的 bug 家族）
2. P1 契约面集中 + 生成（消灭人工同步）
3. P3 业务层切分（降低耦合、恢复可读性）
4. P4/P7 文档与判据分层（让设计重新可读）
5. P5/P6/P8 删除纪律、契约机器化、文件规模

风险：① 收敛期间**真机判据不可丢**；② 任何"删除"必须同批给出替代与沿革；③ 不得借重构引入新 CLI/旁路（用户硬约束）。
