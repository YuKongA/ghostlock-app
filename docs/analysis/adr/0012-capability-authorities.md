# ADR-0012：接口声明能力与 backend 提供能力各有一处权威文件

- 状态：**Accepted**（**用户裁定** 2026-10-09）
- 日期：2026-10-09
- 沿革：由用户在同批提出（原话：接口声明能力和 backend 提供能力应该在上层包和各 backend 下有一个权威文件）；与 ADR-0004（组件模型）、ADR-0006（terminal 归属）同族

## 1 裁定

**两个事实、两个权威文件**：

| 事实 | 权威文件（位置） | 内容 |
|---|---|---|
| **接口声明能力**（上层包对世界的承诺） | **上层包**（`src/core/contract/`）一处 | 该接口**声明**要求各 backend 提供什么能力（能力名 · 语义 · 谁必须提供） |
| **backend 提供能力**（各 backend 实际给了什么） | **每个 backend 各一处**（`src/core/backend/<id>/`） | 该 backend **提供**了哪些能力（能力名 → 实现件 · 是否已接线） |

⇒ 二者由**对拍**约束：**声明 ⊆ 提供** 必须成立 ✓（缺一即具名拒绝，不得静默 ✓）。

## 2 为什么需要（不是形式主义）

1. **本会话已连着吃到同类亏** ✓：步集/词汇面**手抄镜像且无人对拍** ⇒ 改名后产物与枚举**各说各话而无红** ✓；
2. **「能力」目前散落在多处** ✗：`ComponentEntry`（kind+token+selectable）✓ · `ChainSpec.wired` ✓ · `OpSpec` 的 `armed/wired` 两位 ✓ · 各 manifest 的 `available` 列 ✓ ⇒ **没有一个地方能回答「这个 backend 到底提供了什么」** ✓；
3. ADR-0004/0006 已立「identity 是组合唯一权威」✓ ⇒ 本 ADR 把**能力**这一面补上同构的一条 ✓。

## 3 形态（落地时细化）

- 上层包：一份**能力目录** —— 能力名（token）· 语义（一句话）· 必需性（每个 backend 必须 / 可选）+ **编译期断言**（目录自洽 ✓）；
- 各 backend：一份**提供表**（`backend/<id>/capabilities.hpp`）—— 本 backend 的能力 → **实现件路径 + 是否已接线** ✓；
- **对拍**：一条 host 测试 —— 每个 backend 的提供表覆盖目录的**必需项** ✓；**不得**出现目录里没有的能力名 ✗（同「词汇唯一权威」的规矩 ✓）；
- **与既有件的关系**：`kComponents` / `kChainCatalog` / `kOpCatalog` **不撤** ✓（各是词汇/链/op 的权威 ✓）；本 ADR 只新增**能力**这一面的两处权威 ✓，落地时把它们的 `wired/available` 与之**对齐** ✓（防止再出现两处都能回答、答案不同的情形 ✓）。

## 4 未定（动工前出设计）

- 「能力」的**粒度**（原子写 / 步骤 / 一条链 —— 倾向**步骤 + 数据面原语**两级，但需设计稿 + 评审）；
- 与 `op_registry` 的 `armed/wired` 两位的**去重关系**（谁保留、谁改为引用）。
